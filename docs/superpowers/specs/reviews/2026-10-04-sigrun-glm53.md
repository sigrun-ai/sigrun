# Adversarial spec review: sigrun (2026-10-02-sigrun.md, revision 2)

**Angle: feasibility + operational gaps.** Method: read the full spec + CONTEXT.md; evaluated every "verified upstream" claim against the actual Appendix C record; assessed deployment/ops assumptions against the stated single-process/single-replica design. External upstream re-verification was not possible in this session (pi-durable not installed locally; no web tool exposed) — findings below are internal-consistency findings, which is where the real problems are anyway.

## Correct (verified, worth keeping)

- Appendix C is an honest record in one respect: it explicitly lists what is *not* present upstream (skill directory convention, cross-process storage locking) rather than claiming everything. That habit is rare and should be preserved.
- The two-gate structure (§1.2) and independent lanes (§7) correctly separate "shippable" from "safe to decommission hermes," which is the actual risk boundary of this project.
- The decoupling tests ("If the-work-fabric-scrubbed vanished tomorrow…", "If honcho vanished…", §1.3) are falsifiable and the architecture as written passes them.
- §5's "serialized native views, not a bespoke endpoint list" is the right instinct for a thin client — the problem is what it costs under upstream churn (Finding 4).

## Findings

### P0 — The only durable state lives in one SQLite file on an NFS-backed PVC, with zero backup/restore design

**Evidence:** §6.1: "PVC: `4Gi` `REPLACE-nfs-node`". §3.1: "Owns the conversation SQLite (`/data/sigrun.sqlite`)". §6.1 monitoring: "process up, sqlite busy". Nowhere in §3, §6, or §7 does the words "backup", "restore", "WAL", or "journal mode" appear.

**Why this blocks implementation planning:** The spec's entire value proposition is durability ("durable, resumable", §1.3; "crash survival and exactly-once submissions", CONTEXT §3.2), yet:

1. **SQLite on NFS is a known corruption hazard.** SQLite's own docs warn that WAL mode is unsafe on network filesystems (its shared-memory primitives assume local disk), and even rollback-journal mode depends on NFS byte-range locking behavior that varies by server. `REPLACE-nfs-node` is an NFS-backed class. A pod OOM/hard crash at the wrong moment can leave a hot journal that will not recover cleanly over NFS. The spec chose the storage class without any statement about journal mode or this risk.
2. **No backup of any kind.** Hermes's memory survives in honcho (external service), but sigrun's transcripts, cron `defineTask` state, session documents (§5 session-delete flags), and the memo-guard state for memory observation (App B.10) all live in this one file. PVC loss or corruption = total loss of conversation history and every scheduled job's state — the exact things the cutover gate (L3) promises are "durable by construction."
3. **M1 opens the database** ("`Harness.open` over SQLite on PVC", §7 M1). The storage-safety decision (journal mode, storage class, backup mechanism) must be made *before* that milestone, which is the definition of a planning blocker.

**Suggested fix (smallest):**
- Add a §6.1 storage subsection: (a) pin `journal_mode` explicitly (DELETE + `synchronous=FULL` if staying on NFS, or WAL if the file moves to a local-path storage class; the better answer is local-path for the sqlite and NFS only for workspace artifacts, since the workspace is served over `ExecutionEnv` anyway); (b) a scheduled backup — either a Litestream sidecar/carriage or a simple cron `sqlite3 /data/sigrun.sqlite ".backup '/backup/sigrun-$(date).sqlite'"` shipped to RustFS; (c) a restore drill added to the M1 exit criteria ("pod restart resumes" becomes "pod restart resumes *and* a restored-from-backup file resumes").
- Budget: one paragraph of spec + one container or CronJob in the chart. This is cheap; its absence is not.

### P1 — §5 overclaims what Appendix C verified about `requestId` ("exactly-once (verified upstream behavior)")

**Evidence:** §5: "`requestId` makes it exactly-once (verified upstream behavior)." Appendix C's actual record: "`requestId` idempotent submissions, `resume()`, `Conversation.watch()`, `abortSubmission` — **present**, §5 maps onto them."

**Why it matters:** "Present" means the API surface exists. Nothing in Appendix C describes a test of idempotency *semantics* — and "idempotent" (a duplicate has no extra effect) is not the same claim as "exactly-once" (no loss *and* no duplication across crash-replay). The scenario that matters operationally — client submits, pod crashes mid-generation, client retries the same `requestId` after `resume()` — is precisely the case a single-replica Recreate deployment (§3.1/§6.1) makes routine, and it was never exercised.

**Suggested fix:** Reword §5 to "idempotent submissions (API present; crash-replay semantics to be verified in M1)". Add an M1 exit-criterion test: submit → `kill -9` mid-generation → restart → resubmit same `requestId` → assert single completion and no duplicated tool side effects. This is a two-line spec change plus a test that takes minutes.

### P1 — `resume()` crash-recovery is trusted for every restart but was only presence-verified; the memory memo-guard design depends on hook-replay behavior that is unknown

**Evidence:** §3.1: "`resume()` on start" for every boot. §2 (memory): observe rides "`GenerationHooks.afterResponse`/`onYield` … memo-guarded against replay double-observe". App B.10: "memo-guarded so a crash-replay never double-observes." Appendix C: "`resume()`, … — **present**". Appendix C verified the *hooks exist* ("`GenerationHooks` (`afterResponse`, `onYield`, `beforeRequest`) — the … memory-observation seams") but says nothing about **whether hooks re-fire during replay of an in-flight submission after a crash**.

**Why it matters:** The memo-guard is sigrun code that hasn't been written yet, and its required durability depends on an upstream behavior nobody has observed:

- If hooks **do** re-fire on replay, the memo-guard needs durable dedup state (written *before* the observe call, or you can still double-observe), and the "memo" must live in the same SQLite that Finding 1 says has no backup.
- If hooks **don't** re-fire, the guard is trivial — but then a crash mid-response means the observation is *lost* (assistant output committed, memory never updated), which silently degrades L1's parity promise ("Parity with current hermes honcho values", §7 L1).

The same unverified-replay question governs the scarier case: **an interrupted tool call marked `replay: "unsafe"`** (§2 Tools). Does `resume()` re-execute it, park it, or drop it? For chat tools this is cosmetic; for L3 agentic-maintenance/forgejo tools it's the difference between "cutover gate safe" and "agentic-maintenance gets a duplicate rename on every crash." Appendix C never tested a crash mid-tool-call.

**Suggested fix:**
- M1 exit criteria gain: "`kill -9` during (a) streaming response, (b) an in-flight tool call, (c) background compaction → restart → documented, asserted outcome for each." Record hook-replay behavior in an Appendix C addendum.
- L3 exit criteria gain: "unsafe-tool replay semantics verified against a side-effect-free dummy before any agentic-maintenance tool ships."
- Reword App B.10's "memo-guarded so a crash-replay never double-observes" to "memo-guarded — guard design pending the M1 hook-replay finding."

### P1 — Upgrade-risk exposure to a 9-day-old experimental upstream is unmitigated: no pinning, no adapter seams, and the webui wire contract is the upstream view shape

**Evidence:** App B.11: "pi-durable is 9 days old" (against `1.0.2`; `1.0.0` published 2026-10-01 per CONTEXT §3.2). CONTEXT §3.2: "Experimental; the API changes between releases." §5: "serializes the native view/watch frames … with a documented schema so the webui can be built against it." §3.1: "`@earendil-works/pi-durable` (npm, upstream)". Nowhere: a version pinning policy, an upgrade procedure, or a compatibility layer.

**What breaks first when 1.1 ships:** the **serialized `ConversationView`/watch schema**, because it is (a) the newest, UI-facing surface, (b) the thing §5 re-exports verbatim as sigrun's wire contract, and (c) consumed by every webui screen — a field rename there is a simultaneous API + UI break. Second candidate: **the SQLite storage schema** — if `resume()` can't read a 1.0-era file after upgrade, every conversation becomes unreadable, and per Finding 1 there's no backup to roll back onto. Third: the `defineTask`/state-machine API, which would break the cron lane silently (jobs stop waking) rather than loudly.

**Why the current mitigation is inadequate:** there is no mitigation. The spec's decoupling story (§1.3) covers *sigrun's* dependencies on the-work-fabric-scrubbed/honcho, but its deepest dependency — the one it re-exports wholesale — is the one with a stated breaking-change policy and no version strategy.

**Suggested fix (smallest):**
- Pin the exact version in `package.json` (no `^`/`~` ranges) and add a "bump upstream" checklist item: read changelog → snapshot the sqlite file → upgrade on a scratch copy first → verify `resume()` + view serialization → then deploy.
- Confine every upstream touchpoint to a named adapter module inside sigrun (a `viewSerializer`, a `taskWrapper`, a `hooksAdapter`, the provider-contributor shim already implied by §2). The spec already has exactly the right boundaries drawn in §2's table — add one sentence to §1.3 stating that upstream surface contact happens only through these seams, so a 1.1 break is a one-module fix rather than a webui+server+cron simultaneous rewrite.
- Optionally: a CI canary that installs the latest upstream release against sigrun's test suite weekly, to learn about breaks before they're forced.

### P1 — The §5 API is unauthenticated on the tailnet path: Authelia is ingress-only, and the Tailscale LB service bypasses ingress

**Evidence:** §4.4: "Ship gate: Authelia at the ingress (same pattern as grafana). No in-app auth." §6.1: "Service: ClusterIP; Tailscale LB (`tailscale` class) at `sigrun.tailnet.example.test`." §5 prose: "The sigrun server is a thin layer that **authenticates**, serializes …" — with no mechanism defined anywhere. §2/§4.1: "Webui, CLI, Discord — all equal clients" of the §5 API.

**Why it matters:** In this cluster, Tailscale LB services reach the Service directly through the tailscale proxy — they do not traverse the Gateway API ingress where Authelia forward-auth lives (the same split documented for other tailnet services). So the *primary* named access path (`sigrun.tailnet.example.test`) serves §5's write endpoints — `submissions`, `abort`, `configure` — with **no auth at all**, unless the undefined "authenticates" is meant to fill that gap (it currently has no design). Additionally, the ClusterIP Service is reachable from any pod in-cluster. The task's own framing anticipates this: non-browser clients (a CLI, the L5 Discord ingestion, `curl` from scripts) cannot complete an Authelia browser redirect flow, so "ingress covers it" was never true for exactly the clients §2 declares first-class.

**What bites first:** any tailnet device (or anything it runs) can submit to the assistant and steer/abort conversations; a compromised or misbehaving tailnet client has full write access on day one of M2's "user works a full day in sigrun-webui."

**Suggested fix:** Add one §5 subsection: a bearer-token auth layer in the sigrun server (token from a SealedSecret env, multiple tokens allowed so the webui, CLI, and future Discord bot each get one; Authelia path can forward an identity header instead). Define it *now*, because §5's contract is the thing the webui and every channel client are built against, and retrofitting auth into "serialized native views, not a bespoke endpoint list" after clients exist is the expensive direction.

### P1 — Observability covers "process up, sqlite busy" but not the failure mode this architecture actually produces: a wedged harness

**Evidence:** §6.1: "ServiceMonitor + minimal PrometheusRule (process up, sqlite busy)". §3.1: one process runs harness + API + webui; extensions load at boot.

**Why it matters:** The most likely real incident is not a crashed pod (Recreate + `resume()` handles that, per design) but a *live but stuck* process: a generation whose upstream stream wedged (no deadline defined anywhere in the spec), a `watchDoc` wait that never fires, an extension whose boot-time `createProvider` hangs, or an SSE watch that silently dies behind a proxy. In all of those, "process up" is green and the user just experiences a chat that never answers. A second failure mode: one extension throwing at boot — §1.1 promises graceful *absence* ("its absence degrades gracefully"), but says nothing about a *present but failing* extension, which by §3.1's boot order ("load configured extensions → … → `Harness.open()`") plausibly prevents the harness from opening at all: one bad extension release takes down the entire assistant, including chat.

**Suggested fix:**
- Define a `/healthz` in §5 that checks storage writability, `resume()` completion, and extension-boot outcomes (and is *not* the ServiceMonitor's process-up).
- Add two gauges to the PrometheusRule: oldest-in-flight submission age, and oldest-waking task age (a stuck `runtime.sleep`/`watchDoc`). Those two metrics turn "silently wedged" into an actionable alert.
- Add one sentence to §3.1: a failing extension is quarantined at boot (logged, surfaced as a degraded surface) rather than aborting `Harness.open()`.

### P2 — §4.1 lists "Steer — injecting text into a running session" but §5 exposes no steer endpoint

**Evidence:** §4.1 bullet: "**Steer** — injecting text into a running session." §5's endpoint list: submissions, models, abort, configure. §5 mentions "queued submissions" inside the view but never defines submit-while-running semantics (queue vs. interject), so the webui feature has no specified mechanism. **Fix:** one sentence in §5 — either "steer = `POST …/submissions` while a submission is running; the harness queues it (upstream behavior, verify in M1)" or drop steer from the v1 feature list. (Note CONTEXT §1 makes away-from-desk steering a *must-have*, so resolving this ambiguity matters more than its P2 label suggests.)

### P2 — §4.1 "Cron job list (read-only)" contradicts §5 "Deliberately not exposed in v1: … task graph"

**Evidence:** §4.1: "Cron job list (read-only; create/edit later)." §5: "Deliberately not exposed in v1: fork, reset, **task graph**, per-task control." A read-only cron list is a read of the task graph. **Fix:** either exempt a read-only task enumeration from the v1 exclusion (one endpoint: `GET /v1/tasks`) or move the cron list to the L3 lane's webui work, which is where it chronologically belongs anyway.

### P2 — Conversations referencing a *removed* extension have undefined behavior; the spec only covers set *changes* abstractly

**Evidence:** §3.1: "Conversations store extension names, so a deployed extension set change is picked up on restart without touching transcripts." What happens when a resumed conversation references an extension that no longer exists in the deploy-time list — does `resume()` drop those tool definitions, error, or strand the conversation? Given the lanes model (§7) actively encourages enabling/disabling extensions, this path will be exercised often. **Fix:** one sentence in §3.1: "A conversation referencing a missing extension resumes with that surface's degenerate default; the name is preserved for re-enable."

### P2 — §3.2's code example contradicts its own verification note

**Evidence:** §3.2 bullet: `createProvider({ id: "bifrost", baseUrl: <gateway>, auth: apiKey → VK })`; the verification note immediately below: "The provider *auth* lives in `ProviderAuth.apiKey.resolve()`, not a top-level `baseUrl` field" (with resolve returning `{ auth: { apiKey, baseUrl } }`). The example shows `baseUrl` exactly where the note says it doesn't live. **Fix:** correct the example to match the verified shape — it's the snippet the M1 implementer will copy first.

### P2 — "Context files … upstream sections" is a capability claim absent from Appendix C

**Evidence:** §2 row: "**Context files** | section loaders keyed by convention: `SOUL.md` → persona section … | **upstream sections**". Appendix C's verified list contains no section-loader/sections entry (it covers provider, image input, env builder, requestId/resume/watch/abort, defineTask/sleep/watchDoc, compaction+generation hooks, and the two not-present items). If the sections mechanism exists upstream, it's unrecorded; if it doesn't, "upstream sections" is wrong ownership and M1 builds it. **Fix:** verify and either add an Appendix C line or change the row's Inventor to sigrun.

### P2 — No token/cost accounting surface despite verified `cost` on model entries

**Evidence:** §3.2 verification note: "models carrying `baseUrl`/`input`/`cost`." §5's view includes `usage`, but nothing aggregates it. CONTEXT's world runs on carefully-modeled LLM spend (bifrost budgets exist for this reason); sigrun as a 24/7 assistant with cron jobs is precisely the workload where silent spend accumulates. **Fix:** add a Prometheus counter (tokens/cost by model and conversation) to the §6.1 monitoring list; the data is already in the view.

### P2 — Single provider contribution means sigrun inherits bifrost as a single point of failure for *all* model access

**Evidence:** §3.2: `sigrun-ext-bifrost` is "the first real contributor"; §1.1's degenerate env-provider exists only "if none contributed" (§2 boot order: "plus the env default if none contributed"). The deployed configuration will have exactly one contributor. Bifrost is a single replica on its own sqlite PVC; an incident day where the gateway is down (which this cluster has had) takes sigrun's chat *and* its cron jobs (LLM-dependent) dark, with no fallback. **Fix (report-only):** either permit the degenerate env-provider as a *fallback* contribution alongside bifrost (boot order change: merge contributions *and* the env default when a `SIGRUN_FALLBACK_MODEL` is set), or explicitly document "sigrun availability = bifrost availability" as an accepted consequence of the gateway-only policy.

## Summary of angle questions

- **Over-trust beyond Appendix C:** yes — exactly-once (§5) and the hook-replay/memo-guard design (App B.10) both assert behavior the record only shows as "present"; `resume()` crash behavior, restart-survival of `runtime.sleep` (asserted in §2, described-but-untested in App C), and the sections mechanism are all trusted without verification. The provider, image-input, defineTask/sleep/watchDoc, and hooks *seams* are legitimately verified.
- **Upgrade risk / what breaks first in 1.1:** the serialized `ConversationView` schema (wire contract + webui simultaneously), then the sqlite storage schema (unreadable conversations, no backup), then the task API (silently dead cron). Current mitigation: none — fix is pinning + adapter seams + pre-upgrade snapshot.
- **Which operational gap bites first:** Finding 1 (SQLite on NFS, no backup) and Finding 5 (unauthenticated tailnet write API) are tied for first — the storage risk on the first hard crash, the auth gap on the first day of real webui use.
- **Deployment assumptions:** single-process/single-replica is fine at this scale; the hand-wave is `resume()` being treated as proven crash recovery (Finding 3) — its trust is currently justified only as "the API exists," not "the behavior was observed."

Verdict: CHANGES-REQUIRED (minimum: storage-safety + backup/restore design for the SQLite store before M1; crash-recovery verification tests (requestId replay, kill-9 mid-generation/tool-call, hook replay) added to M1/L3 exit criteria; bearer-token auth design for §5 non-browser/tailnet clients; upstream version pinning + adapter-seam policy)
