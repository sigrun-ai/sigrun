## Findings

### P0 — blocks writing the plan

#### P0-1. The approvals seam (`beforeTool`) is asserted as upstream fact but is absent from Appendix C's verified list, and no fallback design exists

**Evidence:** §2: *"pi-durable's `beforeTool` hook can block a call or rewrite its arguments — that hook is the approvals seam, and every approval decision must be stored via the hook's durable memo … (upstream pattern)."* Appendix C's verified list contains: createProvider/stream, image content, `HarnessOptions.env`, `requestId`/`resume()`/`watch()`/`abortSubmission`, `defineTask`/`sleep`/`watchDoc`, `CompactionHooks`/`GenerationHooks`, the sections mechanism, and the not-present list. **`beforeTool` appears nowhere.** (Neither does `defineTool` itself or its `replay: "safe"/"unsafe"` field, though both prior reviews let the tools row pass — the approvals dependency is the one that now carries weight.)

**Why it blocks the plan:** Approvals is a named M1 deliverable ("Approvals extension: conservative default policy + durable memo decisions", §7), a §2 surface, and two §5 endpoints. The entire design rests on an unverified hook *and* on an unverified blocking semantic: can `beforeTool` park a tool call while an external HTTP client decides — across a crash, across a `resume()`? If the hook is synchronous-decision-only (block/rewrite/allow), the "pending approval" architecture needs a fundamentally different mechanism (e.g. block-and-retry via a task, or tool-call-level parking), and the durable-memo/click-allow-crash story changes shape with it. The spec has an established pattern for exactly this situation — the named-M1-verifications list (§5, §7, App C) — and rev 3 used it for requestId replay, hook replay, steer, and journal mode, but not for the one seam where the *mechanism*, not just the *semantics*, is in question. I cannot write the approvals task of the M1 plan without either the verification or a sketched fallback; there is no default I can adopt without designing a subsystem the spec hasn't sized.

**Decision the spec must make:** run the same 30-minute verification the 2026-10-04 provider probe did — confirm `beforeTool` exists, what it can return, and whether a blocked call can await an external decision durably — and add the result to Appendix C. If async blocking is unsupported, the spec must name the fallback design (e.g. "approval = `beforeTool` returns block; the submission is marked awaiting-approval in sigrun state and re-submitted/continued on decision, memo preventing re-prompt") before M1 can be planned.

### P1 — will stall M1 mid-task

#### P1-1. Submission content-part shape and the uploads→submission handoff are undefined, and the one verified image path (base64) is not the designed path (file reference)

**Evidence:** §5: *"`input` carries content parts — text and image/file references (§5 uploads)"*; uploads: *"returns the workspace-relative path used in submission content parts"*. No content-part schema appears anywhere. Appendix C verified: *"Image content in submissions reaches the model (live test answered a color question about a PNG)"* — via **base64** (App B.5: "base64 image in a submission"). So the verified upstream path is inline base64, while §5's design is path-references, with no statement of who translates.

**The implementer must invent:** (a) the part schema (`{type:"text"|"image"|"file", …}` — which fields, is `file` distinct from `image`?); (b) whether sigrun's server resolves path-parts into upstream content (read via ExecutionEnv → base64 / text) before `conversation.submit()`, or passes parts through — i.e. whether upstream's input accepts file references at all (unverified); (c) what happens to a part whose path no longer exists at submit time. M1's core write endpoint cannot be implemented without (a)+(b), and M2's composer/attachment code is built on the same shape.
**Decision:** specify the part schema and name the translator (recommend: server-side resolution to the verified base64/text content at submit; `{type:"text",text}` + `{type:"image"|"file", path, mime?}` in the API). One paragraph.

#### P1-2. The degenerate MemoryBackend's recall depends on an entry-history query API that is not in Appendix C, and the observe record schema is undefined (a cross-lane contract)

**Evidence:** §2: *"recall searches full entry history (including compaction-dropped entries beyond the live context window)"* — no entry-query/list API appears in Appendix C; `Conversation.watch()` presence says nothing about programmatic full-history queries or whether compaction-dropped entries are reachable at all (they may exist only at the storage layer). §3.3: *"an `observe` hook writing per-turn records into a session document"* — the record's fields are never defined, yet L1's honcho implementation consumes the same `observe(record)` contract ("Replaces the transcript-recall default", §3.3), so the shape chosen in M1 becomes the interface honcho must map to.

**The implementer must invent:** the query primitive (fallback candidates: direct SQLite read against the pinned upstream schema — blessed by the same captured-fixture test as §5's drift strategy, but it contradicts the "use upstream as-is" posture and survives upstream upgrades only via the pin; or recall degraded to the live view, which guts the stated feature), and the record schema (minimal defensible shape: conversation id, generation id, role, text, timestamp — but that's my invention, not the spec's).
**Decision:** either verify the entry-query surface and add it to Appendix C, or explicitly bless the fallback ("if upstream exposes no full-history query, degenerate recall reads the pinned-version SQLite schema directly, covered by the captured-schema fixture test") and define the observe record fields. Two short paragraphs; without them M1's memory task stalls at the first type signature.

#### P1-3. Sigrun's side-store mechanism is hedged ("document/table") and the "durable memo" primitive is unspecified — four M1 deliverables touch it

**Evidence:** §5 session-meta: *"Backed by a sigrun session-meta document/table in the same `/data/sigrun.sqlite`"*. §2: *"policy stored per conversation in a document"*; *"replay-guard via a durable memo"*; §2 Approvals: *"stored via the hook's durable memo … (upstream pattern)"*. §2 also implies an upstream document store exists (`watchDoc` for event-driven wake — verified in App C). So: does sigrun use upstream's document store (gaining `watchDoc` wake for free, whatever its actual API is), or create its own tables inside the harness's SQLite file (co-owning a file whose schema and migrations upstream owns — the §5 upgrade procedure's "upgrade on a scratch copy" must then also cover sigrun's tables)? "Durable memo" is used three times without saying whether it's an upstream API or sigrun's own keyed writes.

**Decision:** one paragraph naming the mechanism (recommend: own tables in the same file, prefixed, with the upgrade drill covering them; or upstream docs if the verified API supports keyed per-conversation records). This choice is load-bearing for session-meta, approval memos, memory observe records, and the crash battery's hook-replay findings — M1 shouldn't reach it by accident.

#### P1-4. The backup CronJob is under-specified: target, credentials, retention mechanics, restore ownership, and same-node RWO co-scheduling are all unnamed

**Evidence:** §6.2: *"nightly `sqlite3 .backup` to the NFS/RustFS path (CronJob in the chart), retention ≥ 30 days"*; §6.1 names no backup values at all. The task's question is exactly right — the chart section doesn't name what the CronJob needs:
- **Target choice:** NFS vs RustFS are different implementations (NFS: a mounted PVC + path + file retention by deletion; RustFS: per-namespace S3 API key + endpoint + bucket, retention by explicit delete or lifecycle — RustFS lifecycle behavior unverified here). "NFS/RustFS" is a slash, not a decision.
- **Credentials:** whichever target, a SealedSecret + env wiring; §6.1's secret list is extension-only ("whatever the *enabled* extensions need") — backup creds are core, not extension.
- **Node co-scheduling:** the sqlite PVC is local-path (node-bound, RWO). The CronJob must mount the *same* RWO volume, which constrains it to the same node — it needs the same worker nodeSelector + `dedicated=workload` toleration the Deployment has (both pools are tainted in this cluster). Unstated; a naive CronJob will hang in Pending.
- **Image:** needs `sqlite3` in it (busybox doesn't have it).
- **Restore ownership:** M1's exit says "a restored-from-backup file must resume" but no procedure exists anywhere (scale Deployment to 0 → replace file via a job/kubectl cp → scale up — owned by chart docs? a repo runbook?). This matters double because of a fact the spec doesn't surface: the cluster's DR posture **explicitly does not preserve local-path PVCs** (`flux-cluster/docs/runbooks/pre-disaster-pvc-inventory.md`: "CNPG local-path WAL (not preserved — recreated fresh)") — the nightly backup is the *only* disaster copy of sigrun's transcripts, so the restore path is not optional plumbing, it is the DR story.
- **Capacity context (minor):** the local-path partition has a historical fill incident (`flux-infrastructure/cnpg-system/catalog-trixie.yaml` comment: "the local-path partition filled") — sqlite is small, but the PVC size and the backup target's quota are unspecified.

**Decision:** name the target (recommend RustFS `s3://` per the CNPG barman precedent (the deployment's existing RustFS endpoint, now recorded in `docs/private.md`), or NFS for simplicity), the secret, the retention mechanism, the node co-scheduling, and the restore runbook owner. Half a page in §6.1/§6.2.

#### P1-5. Crash battery items #2 and #3 lack success criteria — "documented by observation" and "transcript consistent" are not pass conditions

**Evidence:** §7: *"`kill -9` mid-tool-call → safe/unsafe replay semantics documented by observation; `kill -9` during background compaction → transcript consistent."*
- **Mid-tool-call:** the task's question is exactly the gap — what is the *expected* unsafe-tool outcome? If `resume()` re-executes an unsafe tool, is the battery passing (record and code around it) or failing (blocker to escalate upstream)? If it parks it, is parked-without-restart acceptable? The implementer must invent the acceptable-outcome table, and that table determines whether L3's mutating maintenance tools are safe to build at all.
- **Mid-compaction:** "consistent" is undefined. Workable definition exists (resume() succeeds; entry set is a prefix-closed superset — no half-written summary entry; view serializes; subsequent submits succeed) but the spec doesn't give it, and "consistent" could also be read as "no entries lost" (a much stronger, possibly unachievable claim — losing the in-flight turn is fine; losing *committed* turns is not).
- Minor: deterministically triggering "during background compaction" needs a forcing setup (tiny `reserveTokens` to make compaction fire on cue) — not stated, discoverable, but the plan should name it so the battery isn't hand-waved.

**Decision:** define the pass criteria per battery item: for #2, the acceptable-outcome enumeration (safe: re-execution OK; unsafe: must NOT silently re-execute — parked or failed-with-visible-state, plus what the memo must then record); for #3, the concrete checks listed above. One bullet each.

#### P1-6. `createConversation()` and `configure()` are asserted upstream primitives absent from Appendix C's verified list

**Evidence:** §5: *"create a conversation (upstream `createConversation()`)"*; *"`POST /v1/conversations/:id/configure` — model/thinking changes via `configure()`; accepted fields enumerated in the captured schema."* Appendix C's conversation-surface record is exactly: *"`requestId` idempotent submissions, `resume()`, `Conversation.watch()`, `abortSubmission` — present."* Neither `createConversation` nor `configure` is in it, and the "accepted fields enumerated in the captured schema" presupposes a capture that doesn't exist yet. The prior review's P0-1 forced these endpoints in (correctly), but the verification record was never extended to cover the primitives they wrap. If either doesn't exist in the assumed shape, the v1 endpoint list's first item and the configure item stall on discovery — the exact class the task names.

**Decision:** verify both against the pinned package (minutes, same as the 2026-10-04 probe) and add to Appendix C; or move them to the named-M1-verifications list with the fallback named (e.g. "if no `createConversation`, creation is a storage-layer insert via the harness's own open path — sigrun owns the app-side index anyway").

#### P1-7. Session-meta: fields are enumerated but not typed, PATCH merge semantics are undefined, and the session↔conversation identity is implicit

**Evidence:** §5: *"the app-side session metadata (pinned, tagged, archived/hidden, composer draft, `source`: `user|cron`)"*; *"Backed by a sigrun session-meta document/table"*. Unspecified: is `tagged` a free string list, per-session? Is `composer draft` text only or does it carry pending attachments (hermes's draft includes the attachment tray)? Does `PATCH` replace or merge (merge with `null`-to-clear semantics needs a convention)? And the URL says `/v1/sessions/:id/meta` while every other path says `/v1/conversations/:id/...` — the 1:1 mapping is implied by "multi-**session**, single-user" + `createConversation()` but never stated, and the plan author must decide whether "session" is an alias or a distinct resource. Small individually, but this is the resource the entire sidebar (M2's flagship surface) reads.

**Decision:** one table: field, type, PATCH semantics (recommend merge, explicit `null` clears), plus one sentence: "session ≡ conversation; `/v1/sessions/:id` is an alias of `/v1/conversations/:id`" (or rename the path).

#### P1-8. Uploads require an ExecutionEnv write primitive that is not verified, and the view-serialization projection is unstated

**Evidence (two linked smalls):**
- §5: *"materialize an uploaded file into the conversation's workspace via its ExecutionEnv."* Appendix C verifies the env *builder* (`HarnessOptions.env(target, context)`) but says nothing about what an ExecutionEnv can *do* — a write-file method is asserted by implication. For the static local workspace this is trivially implementable (sigrun knows the path), but the spec's justification — *"This keeps the upload path correct for remote workspaces (§3.4)"* — leans on the unverified primitive. For the static-workspace M1, the implementer must decide whether uploads go through the ExecutionEnv abstraction now (correct shape, needs the primitive) or direct-fs with a TODO (works, but violates the stated design rationale).
- §5: *"serialized per the captured schema (below)"* — "below" is a paragraph *describing* a future fixture, not a schema. Whether `ConversationView` is directly JSON-serializable (or holds non-JSON members — streams, functions, live handles) is unknown; the projection rules (what's included/excluded/renamed in the wire frame) are a real design decision the M1 server task must make before writing the fixture.

**Decisions:** (a) verify or bless a fallback for the ExecutionEnv write method ("M1 uploads write directly to the resolved static workspace path; the ExecutionEnv path lands when the primitive is verified"); (b) state that the M1 server task's first deliverable is capturing the fixture by serializing a real view and committing it, with the projection defined then — explicitly, so it's planned work rather than discovered work.
