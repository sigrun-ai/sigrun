# Review: `docs/superpowers/specs/2026-10-19-sigrun-core-hardening-design.md`

Read-only review; nothing was edited. Every factual premise below was checked against `src/`, `test/`, `webui/src`, `tui/src`, `charts/`, `Dockerfile`, and the pinned `node_modules/@earendil-works/pi-durable/dist/**/*.d.ts` (1.2.0). Line numbers are from the current working tree.

## Blockers

**B1 — Admin token-minting for other users contradicts "admin is configuration authority, not content authority" (§5.4 vs §5.6).**
§5.6 rules that admin grants no read of another user's private resources. But §5.4 gives admins `sigrun token create <name> --user <u>` (CLI) and "admins manage anyone's" tokens (`POST /v1/auth/tokens`), and "the token carries that user's rights." A token bound to user B *is* user B for every content route — an admin who mints one reads B's private conversations, answers B's interactions, and forks B's content. That collapses the headline ruling. Evidence of the strictness the spec otherwise intends: admin is deliberately excluded from `:id` routes and lists (§5.6), and the sharing model gives even the owner's write-sharees only what the owner granted. Smallest fix: restrict admin token API/CLI to **list and revoke** other users' tokens; creation is self-only (plus `SIGRUN_API_TOKEN` for bootstrap). If impersonation is wanted, it must be an explicit ruling that amends §5.6's wording.

**B2 — `DELETE /v1/users/:user` permanently locks the deleted user's content; `accessOf` has no rule for a nonexistent owner (§5.8 + §5.9).**
The spec says deletion "revokes their tokens and leaves their resources in place, owned by a removed user." Walk the access rules: `sharing` defaults to `private`; `accessOf` grants write to the owner (gone — no principal can match a removed username), household only for `household` scope, and admin has no content access (§5.6). Result: every private conversation of a deleted user is invisible to *everyone*, and — since conversation deletion is a declared non-goal (§12) and even `PATCH …/meta` (archive) needs write — the content is permanently unreachable and unmanageable. Smallest fix: define the semantics in §5.9 — e.g. deleting a user converts their resources to ownerless (household-write per the ruling), or adds an admin *transfer-ownership* action (configuration authority, not content read), or forbids deletion of users who own content.

**B3 — The `proxy` trust model as specified lets any trusted-CIDR peer forge identity and admin (§5.2/§5.3).**
The mechanism (socket-peer ∈ `trustedProxies`) is sound, but the spec's example and docs guidance — `"trustedProxies": ["10.42.0.0/16", "fd00:42::/56"]` and "dual-stack clusters list both pod CIDRs" — trust the *entire pod network*. `proxy` is tried first in the intended `["proxy","token"]` order, so any pod that can reach the Service can send `Remote-User` + `Remote-Groups` and become an admin user in `adminGroups` — no Authelia, no cookie, no token. The "proxy must OVERWRITE these headers" note only covers traffic that transits the proxy; direct in-cluster requests bypass it. Smallest fix: keep the mechanism, change the guidance — `trustedProxies` should name the ingress/proxy workload identity as narrowly as k8s allows (specific pod IPs/labels or a dedicated CIDR), and the spec must state explicitly: *every peer in `trustedProxies` can forge any identity, including admin*. If whole-pod-CIDR trust is the accepted homelab posture, say so as a ruling; don't leave it as the default-looking example.

## Should-fix

**S1 — `/v1/auth/login` is unreachable under the rules as written (§5.2/§5.4).**
Under `methods: ["token"]`, "a non-empty list with no match returns 401" — but the webui's first request after a 401 is `POST /v1/auth/login {token}` carrying *no* credential (the body token is the credential). The spec never exempts the login (and logout) routes from the authenticator gate, so the cookie flow it defines cannot boot. Fix: state that `/v1/auth/login` is public-by-design (token-in-body is the credential) and note the brute-force posture (even a homelab wants *some* failure delay/count on this one endpoint; nothing else in the spec rate-limits).

**S2 — Setup/invite codes have no storage or lifecycle story (§5.8).**
Generation, logging, and the `<stateDir>/setup-code` file are specified for the *setup* code, but invites (admin-issued, expiring, single-use, "the setup code is the first invite") have no defined store: which file, durable across restarts or in-memory, how expiry and single-use are enforced transactionally, and how the claim serializes against concurrent invite redemption (the 409 serialization is specified only for the *initial* claim). Also unimplementable as written: "`token` is returned when `token` is among the methods **(or the caller is the TUI)**" — the server has no way to know the caller is the TUI. Fix: one code store (`<stateDir>/invites.json`, hashed like tokens, `expiresAt`, `usedBy`), and replace the TUI clause with an explicit request flag in the claim body.

**S3 — Last-admin and admin semantics are ambiguous once admin can come from proxy groups (§5.6/§5.8).**
"Demoting or deleting the last admin is a 409" — but a proxy user's admin is derived per-request from `adminGroups` (§5.1), not from the record. The last-admin check must count group-derived admins, and §5.8's auto-provisioning must say what lands in the record's `admin` field when the provisioning request's groups already intersect `adminGroups` (and what happens when Authelia later drops the group — per-request loss of admin while the record still says `admin: true`, or the reverse). One paragraph fixes it.

**S4 — `groups` in people-scope sharing has no data source (§5.9 vs §5.8).**
`{ scope: "people", users, groups?, level }` — but directory entries (§5.8) are `{user, name?, email?, admin, createdAt, source}`: **no groups field**. Groups exist only as per-request proxy headers. So group matching in `accessOf` is undefined for token users (no groups ever) and is a live-vs-snapshot question for proxy users. Simplest fix for v1: cut `groups` from `Sharing` (it can be added with OIDC, which is the actual groups source), or define it as the provision-time snapshot on the directory record.

**S5 — §8.3's "household-visible" understates what §5.9 grants for ownerless jobs.**
`accessOf` makes ownerless resources household-**write** (§5.9), and §8.3 says file/extension jobs without an owner are ownerless. PATCH/DELETE are blocked by `job_declared`, but **`POST /v1/jobs/:id/run` needs only write** — so any directory user can fire system-declared jobs, and each fire creates an ownerless conversation that is itself household-write (anyone can chat into the cron run). That may be intended; the spec should say it in §8.3 instead of the weaker "household-visible," and the TUI/webui will render other people's system jobs as runnable. Related gap in the same section: the `prompt` action's `model`/`thinking` fields are unspecified for `conversation: <fixed-id>` runs — applying them would mutate the user's configured conversation; say whether they apply only to `conversation: "new"`.

**S6 — §6.7's deletions have an undeclared sequencing dependency on an out-of-scope repo.**
Deleting `ExtensionSubmit`/`submitBindings`/`memorySubmit` (they exist: `src/server/index.ts:914-916`, `src/harness/boot.ts:535`, `src/harness/loader.ts:104,129,211`) is only safe once sigrun-ext-memory-markdown has moved off the submit-binding path (the memory-seam plan's port). The spec conditions only the named-export bridge removal on "once memory-markdown ships a default export"; the submit deletion needs the same explicit precondition (plus a compat window — named-export factories are a supported form today, `loader.ts:266,541`, and third parties may use them; the spec drops them without a deprecation release).

**S7 — §7.3 delta frames are the spec's largest complexity-per-benefit item; consider deferring.**
R8 is real and verified (below), but its cost is bandwidth, and the wire contract already makes full snapshots subsumable. A coalesced/throttled snapshot stream (e.g., ≤4 full views/s, or 100 ms trailing-edge coalescing — upstream already commits at `partialIntervalMs` = 100 ms) fixes the 10×/s storm with a ~20-line change and zero client migration. Delta frames instead buy: a shared reducer in `src/shared/`, per-stream diff state, a property test, changes to *both* clients, and a new captured-schema fixture — the riskiest single surface in W3. Recommend: ship the throttle in W3, keep delta frames as a follow-up only if measurements still demand them. (If the user wants deltas now, the section is internally fine — the `steer` projection and doc-kind diffing are correctly derived from the upstream view shape.)

**S8 — Token/user files mutated by CLI while the server runs: define store semantics (§5.4/§5.8).**
`sigrun token create/revoke` and `sigrun user add` write `api-tokens.json`/`users.json` in the config dir — the same files the running server reads. Say whether the server re-reads per request, watches mtime, or requires restart; otherwise CLI recovery while the server is up (the common case for "revoke a leaked token now") has undefined behavior. One sentence + one test ("CLI revoke is honored by a running server") closes it.

**S9 — Extension slash commands have no access rule (§9.3).**
`POST /v1/conversations/:id/commands/:name` runs extension code with `host` — but the spec never says what access the caller needs on the conversation. Everything else in W3/W5 is explicit (submit=write, read stream=read). Fix: commands require write on the conversation (they can submit via `host.conversations`).

## Nits

- §5.1: "principal.user is a username in the user directory" is false under method `none` with an arbitrary `X-Sigrun-User` (the whole point of naive mode). Soften to "under `token`/`proxy`; under `none` it is the unverified header value."
- §9.6: `url` is "built from `server.publicUrl`" — say what happens when it's unset (omit `url`).
- §5.8 vs §9.2: while unclaimed, "every `/v1/*` route except `/v1/onboarding*`" 403s — that includes `public` extension routes; pick (a 403 is probably right; just note it).

Spell out which.

## Verdict

**OK with notes** — the architecture is coherent, the pi-durable premises are accurate (several are load-bearing and all checked out), and the access model is nearly right. B1–B3 are design holes that should be resolved in the spec before implementation plans are written; S1–S9 are one-paragraph fixes. The single best simplification available is S7 (throttle-first instead of delta frames).

## Addendum (R4 evidence, post-warden challenge)

Warden challenge accepted — the causal chain in question is R4 ("no `bodyLimit` set anywhere → Fastify's 1 MiB default kills phone photos"). I had verified sigrun's half but asserted the 1 MiB default from memory. Both halves are now checked against the pinned package:

**Evidence, from this run:**

1. **sigrun sets no `bodyLimit` anywhere** — `grep bodyLimit src` → **No matches** (this run). The uploads route (`src/server/index.ts:1694`) and the import route inherit whatever the factory default is.

2. **The pinned Fastify default is 1048576 bytes (1 MiB)**:
   - `node_modules/fastify/lib/config-validator.js:6` — init-options schema: `"bodyLimit":{"type":"integer","default":1048576}`
   - `node_modules/fastify/lib/config-validator.js:30-31` — `if(data.bodyLimit === undefined){ data.bodyLimit = 1048576; }`
   - `node_modules/fastify/lib/config-validator.js:1265` — `defaultInitOptions` includes `"bodyLimit":1048576`
   - `node_modules/fastify/fastify.js:887` — `options.bodyLimit = options.bodyLimit || defaultInitOptions.bodyLimit`
   - `node_modules/fastify/test/body-limit.test.js:111` — upstream's own test: *"default request.routeOptions.bodyLimit should be 1048576"*
   - Exceeding it is a 413: `node_modules/fastify/docs/Reference/Errors.md:382` (`FST_ERR_CTP_BODY_TOO_LARGE` — "request body is larger than the provided limit").

So the R4 causal chain is fully verified with package evidence: base64-JSON uploads are capped at 1 MiB of body, which is < 1 MiB of photo bytes after the ~4/3 base64 expansion — a typical phone photo (2–8 MB) cannot pass. The review's R4 finding and the spec's §6.2 raw-upload fix stand as written; nothing in the review needed correction.

**One adjacent premise I cannot check from this repo**, stated plainly rather than silently assumed: the §5.4 claim that a `sigrun_session` cookie keeps the existing SSE stream working depends on browsers sending same-origin cookies on `EventSource` requests without `withCredentials`. That is WHATWG browser behavior, not repo code — no tool in this run (or available to me) can execute a browser to confirm it. The repo-side halves *are* verified (webui uses the native `EventSource`, `webui/src/stream.ts`; `baseUrl` defaults to `""` = same-origin, `webui/src/api.ts` `SigrunClientOptions`). The browser-side behavior itself should be pinned by the W1 e2e test the spec already lists ("cookie login works for SSE") rather than taken on trust.
