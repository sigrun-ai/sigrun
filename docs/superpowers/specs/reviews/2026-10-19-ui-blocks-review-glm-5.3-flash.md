## Review — `2026-10-19-sigrun-ui-blocks-design.md`

**Verdict: BLOCK** — three design holes a plan-writer cannot resolve without rulings (interaction answer shape, "no access" representation, tree byte budget). The rulings 1–16 are otherwise implemented faithfully, §5 matches the sizing tally almost exactly, and the pi-durable/pi-tui seams the spec leans on are real.

### Blockers

**B1. Multi-question interactions cannot produce the unchanged `{ids, values, text}` answer.**
§9.1 maps `answer {ids, values, text}` from "the `choice` field's value is `ids`, the other fields are `values`" (spec line 635) — that reading assumes exactly one `choice` field. But the same section's ask-user-question port is "1–4 questions, each a `section` … holding one `choice`", and §16 requires both "answers keep their `{ids, values, text}` shape" (line 987) and "a four-question ask-user-question tree … answers in one submit". Four choice fields yield four id lists; today's `InteractionAnswer` has a single `ids?: string[]` (`shared/src/interactions.ts`). Evidence: the answer route is declared "unchanged" while the body that feeds it changed shape. Fix: define the flattening rule — single-`choice` interactions keep `ids`; multi-question trees serialize per-field (`values[<fieldName>] = id[]`) — or widen the answer type; then make the §16 test assert the chosen shape.

**B2. There is no representation for "principal without access", yet three sections depend on one.**
`render` returns `access: "read" | "write"` only (line 465); §6.5 and §7.2 define only `500 surface_failed` for throwing renders. §16 nevertheless requires "a principal without access gets no event and a 404 on fetch" (line 969). The mechanism is undefined: does render throw a distinguished error? Is denial a 403 or an existence-hiding 404? Same gap one level up: line 509 sends `surface.changed` "to every connected principal subscribed to that surface instance", but the W3 stream it builds on defines one SSE stream per client "filtered by what the caller can read (§5.9)" with **no subscription protocol** (`2026-10-19-sigrun-core-hardening-design.md:732-747`), and a surface is not a §5.9 owner/sharing resource, so the server cannot filter it without calling the extension. Fix: add a denial contract (e.g. render may throw `SurfaceForbidden` → 404 on surface/data routes, event suppressed) and pin the subscription rule — simplest is broadcast-to-authenticated (the event carries no data) plus the 404; say which.

**B3. Tree bytes are unbounded; the one stated cap points at the wrong place.**
§4.5 limits block *count* and *data-model* size only. A 512 KiB data URL lives in the tree (`image.src`), yet line 716 counts it "in the data limit" — the data model is a separate JSON object (§3, §7.2 returns `tree` and `data` apart). 200 chat blocks × 512 KiB ≈ 100 MB of tree per render, fanned to every connected channel and stored durably as a `sigrun.blocks` entry (§8.2). Fix: add a per-placement tree byte cap to §4.5 (e.g. 256 KiB chat / 2 MiB view) and count data URLs against a single combined "surface size", deleting the misleading clause.

### Should-fix

**S1. SSRF range check has a rebinding TOCTOU.** §11.2 (line 729) "DNS-resolve first and refuse …, re-checked on every redirect" — but a second resolution at connect can return a different (private) IP; §15 then overclaims "the range checks prevent SSRF". Also missing from the deny list: IPv4-mapped IPv6 (`::ffff:127.0.0.1`), `0.0.0.0/8`, multicast. Fix: dial the validated IP set directly (custom lookup in the fetcher), re-validate at connect and on each of the ≤3 redirects.

**S2. HMAC key lifetime is unstated.** §8.2 stores `{tree}` durably; §11.1 rewrites https→proxy "before the tree leaves the server", so signatures are recomputed per serve — fine — but the cache (line 733) and any client-held signed URL must survive restarts. One sentence needed: key persisted under the data dir (and rotated how?).

**S3. Read-only enforcement is ambiguously keyed.** §15 line 952 rejects actions on "a surface whose last render returned `access: 'read'`" — per instance, or per (principal, instance)? Two principals with different access share an instance; a demoted user keeps acting until their next render. Fix: "the acting principal's most recent render of that (id, key) instance; a miss defaults to read."

**S4. Change-note timing vs pi-durable queueing.** §8.3 line 575 appends "one context entry … at the start of the agent's next turn". Evidence: a custom entry is only prompt-visible if the write carries a `model` message ("a write of only `kind` and `data` … changes nothing the model sees"), and context-affecting writes issued while busy queue in `pi.inbox` (`node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts:594-600`). So ordering of (note, triggering input) is unpinned, and under `whenBusy: "steer"` the note can land after the steer. Fix: pin that core writes the note (with its model message) on the submit path before the input is admitted — note entry precedes the user entry — mirroring how §8.4 answers fold pending changes into the message itself.

**S5. Two shapes are missing entirely.** `sort?`/`filter?` on `collection` (line 276) have no type anywhere — and no sizing case actually binds a filter *on the collection* (all filters are `form(mode: live)` sketches); `UploadedFile` (line 468) is undefined (name? bytes? MIME?). Fix: type them or cut `filter?` and let filters stay forms; define `UploadedFile {name, mime, bytes}` and where uploads land (§7.2 caps by `maxBytes` but says nothing about storage/disposition).

**S6. Event wiring props are declared only in §14.1, not in the block tables.** §14.1 line 900 names `onMove`, `onSubmit`, `onCheck`, `onActivate` and the example uses `onMove: "move"` (line 892), but §5.5's table has only `itemAction?`/`reorder?`/`checkable?` with no handler-name props, and `page.actions[].action` (§5.1) is untyped. Without these, §6.3's `{action, payload}` has no tree-side source. Fix: add `onMove?`/`onCheck?` to §5.5 (`onActivate?` = `itemAction`), type the page `action` field, and state that a name with no registered handler fails validation (already promised in §14.1).

**S7. Ambient envelope silently narrowed.** §9.2 line 665: `place: status | panel`, `budget`, `refresh` — today's record is `place: "status" | "footer" | "panel"` with `maxRows`/`overflow`/`refreshMs` (`shared/src/ambient.ts`). Dropping `footer` contradicts the seam doc's strongest consumers (pi-zentui/pi-powerline own the footer, `docs/approval-ux-seams.md:241-243`). Fix: keep `footer` or state its removal with a reason; enumerate the full new envelope (owner? overflow?) since ruling 16 forbids legacy shapes and U6 needs the exact schema.

**S8. Interaction envelope listing is factually wrong.** Line 637: "The envelope (`key`, `interactionKinds`, `expiresAt`, `answeredBy` …)". Interactions have no `key` — the join key is `callId` (`shared/src/interactions.ts`); `interactionKinds` is a factory-result declaration (`src/harness/loader.ts:303`), not an envelope field. Fix: `kind`, `callId`, `expiresAt`, `answeredBy`, first-answer-wins.

**S9. H2's header view-toggle has no home.** The sizing sketch puts `view: choice(board|list)` in `page.actions`; but `switcher` "selecting navigates" (§5.1), actions are buttons, forms can't sit in the header, and `display` as a data binding (needed for `display: $view == …`) is nowhere licensed in §4.2. Fix: one sentence — the toggle is `navigate(params)` (extension reads `params.view`, cheap since the tree is static) or a live form under `/view/` — and say whether structural props like `display` accept bindings.

**S10. H8's `share(bar)` table cell isn't in the v1 set.** `columns` (§5.5) allows `format` only; no `bar` cell kind exists despite the sizing tally keeping the table display partly for it. Fix: drop it from the worked example or add a column cell kind to §5.5.

### Nits

- **N1.** §8.2 line 559 "Forks copy it, so a fork starts from the state at the fork point": pi-durable gives `fork: "current" | "initial"` for latest-only and `"asOf"` only for rewindable families (`pi-durable/dist/types.d.ts:31-40, 543-551`). Sigrun forks at an arbitrary entry, so the claim requires `history: "rewindable"` + `fork: "asOf"` — pin it, or accept latest+`current` (state at fork time) and reword.
- **N2.** §11.2 admits AVIF but pi-tui has no AVIF dimension parser (PNG/JPEG/GIF/WebP only, `pi-tui/dist/index.d.ts:31`), and kitty renders non-PNG as text without a registered transcoder (`dist/components/image.d.ts:9-10`); §11.1's data-URL list excludes AVIF. Simplest: drop AVIF everywhere or note the kitty transcoder requirement.
- **N3.** §9.1 says option `tone` "carry[ies] over", but vocabularies differ: today `"danger"|"warn"|"ok"|"neutral` vs block `bad`/`good` (§10.1). State danger→bad, ok→good.
- **N4.** §4.2's relative binding `./title` extends JSON Pointer without defining it; one sentence ("inside an item template, `./x` resolves against the item object").
- **N5.** §5.7 allows `image` in `interaction`; no sizing case needs it (C2). Cut or cite.
- **N6.** §5.6 `choice.display: chips` has no sizing case; cut or cite.
- **N7.** §4.3/§6.3: extension-returned `DataUpdate`s carry their own `rev`; say the server assigns revs, or two writers on a `sharedData` surface can collide.
- **N8.** §8.1 `update_blocks`: define the tool result (return the updated text projection) — after user edits, the model's stale-index `move` ops otherwise misplace silently.

### Checked and sound

Security posture otherwise matches the claims: markdown escapes HTML with scheme-allowlisted links (§15); HMAC-gated proxy with signed-at-serve rewrite; data/asset sources enumerated with traversal rejection (§11.1); action dedup via `actionId` and `requestId = "blocks:" + actionId` (line 602) maps onto pi-durable's host-provided `requestId` dedup (`SubmissionRecordBase`); §8.3's append-only change note is implementable without rewriting earlier entries (entries are append-only; `submit({type:"write"})` exists). §5's block set matches the sizing tally line-for-line except S10; the "no other ext repo writes interaction/ambient records" claim verifies against `~/repos/sigrun-ext-*` (approvals is the sole writer; memory-markdown is seam-only). Contradictions with the core-hardening spec: none beyond B2/S7/S8 (W5 `surfaces` field follows the documented factory pathway; §13.4's raw-JSON fallback matches §7.7; `server.maxUploadBytes` referenced is the planned knob, correctly named).
