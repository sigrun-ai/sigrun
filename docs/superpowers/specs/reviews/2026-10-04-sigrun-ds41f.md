## P0 — blocks implementation planning

### P0-1. §5 v1 has no conversation creation/listing, yet §4.1 ships a multi-session sidebar and §5 itself defines multi-session semantics

Evidence, §5: *"the root conversation is a single reserved conversation upstream; v1 is single-user against it. The multi-user path (v2) creates explicit per-user conversations + a user→conversation mapping document, **and adds a conversation-creation endpoint**."* Immediately below, §5 defines *"**Session delete:** … 'delete session' is an app-side session document (archived/hidden flag) the sidebar reads"* — archived/hidden is only meaningful with many sessions. §4.1 requires *"sessions sidebar (pinned/tagged, `⋯` menu)"* and *"Per-session persistent composer draft"*, and §7 M2's exit is a full day at parity. hermes-webui's daily surface is explicitly multi-session (`sessions.js` `/api/sessions`, `/api/session/new` at `ui.js:22349`, pin/archive/delete at `sessions.js:4891-5537`).

So v1 as specified has exactly one conversation: the sidebar has one row, pin/tag/archive/delete/draft are dead code, and the M2 exit criterion ("works a full day at hermes parity") is unreachable because the user cannot start a second conversation. Worse, the plan cannot be written: M1's deliverables list contains no creation or listing endpoint, and no owner is named for the app-side session-metadata document.

Fix (smallest): in §5, split *ownership* (v2) from *lifecycle* (v1). Add to the v1 endpoint list: `POST /v1/conversations` and `GET /v1/conversations` (plus `GET/PATCH /v1/sessions/:id/meta` for archived/pinned/tagged), and state where that app-side document lives (a sigrun table in the same `/data/sigrun.sqlite`, per §3.1's single-process ownership). If pi-durable genuinely has no creation primitive, say so and name the M1 task that builds the reserved-root-plus-app-side-index instead — the point is that M1's deliverable list must contain whichever it is.

### P0-2. §5 exposes no surface for scheduled jobs, yet §4.1 ships a cron list at the ship gate

Evidence, §4.1: *"Cron job list (read-only; create/edit later)."* §5's endpoint list is: views/watch, `POST …/submissions`, `GET /v1/models`, `POST …/abort`, `POST …/configure` — nothing that enumerates jobs. §2 scheduled jobs: *"pi-durable `defineTask` state machines"* — in-process definitions, not a queryable registry; `defineTask` gives no listing or last-run/next-run state. So the ship-gate cron panel has no contract to build against, and the M2 audit (§4.3) cannot decide whether hermes-webui's cron panel code is portable (`panels.js:1047-2169` is a full CRUD client over `/api/crons*`).

Fix: add a v1 surface, e.g. `GET /v1/jobs` → `[{name, schedule, lastRun, nextRun, state, lastError}]` and `GET /v1/jobs/:name/runs`; assign ownership (core task registry vs `sigrun-ext-cron` exposing it) and state the empty-case (no cron extension → empty list, panel renders empty state). Alternatively drop the cron panel from §4.1/M2 and move it wholly into L3, and say so.

### P0-3. Approvals/permissions are missing from the §2 surface list, but the tool contract is "use it as-is"

Evidence, §2 Tools: *"pi-durable `defineTool` — TypeBox schema, `replay: "safe"/"unsafe"`, per-call ExecutionEnv | upstream | none needed."* §4.1's parity list does not mention approvals at all, yet hermes' daily UX is dominated by the approval card and its YOLO toggle: `messages.js:7591-7909` (`showApprovalCard`, `_approvalSessionId`, owner-scoped polling), `commands.js:2030-2075` (`/api/session/yolo` enable/disable), `boot.js:2489` (Enter = "Allow once"). "hermes-with-nothing-enabled parity" (§1.2) still prompts for approval — the toolset isn't what gates it. If pi-durable has no tool-call approval/interrupt path, there is (a) no parity, and (b) no contract for an extension to add one; and if it *does*, §2 must say so and §5 must expose the pending-approval state plus a respond endpoint, because approvals are inherently a client interaction — the §5 "serialized native views" model has no write path for "allow once".

Fix: add an **Approvals** row to §2 with the mechanism (upstream hook if it exists, else a sigrun contract), and add `POST /v1/conversations/:id/approvals/:id {decision}` + the pending-approval field in `ConversationView` to §5. Decide where policy (yolo/allowlist) is stored and whether it is per-conversation or global.

### P0-4. §5's "serialized native views" is an unversioned dependency on an experimental upstream, with no drift detection

Evidence, §5: *"the native `ConversationView` … serialized as-is, with a documented schema so the webui can be built against it"*; §1.3/CONTEXT §3.2: *"Experimental; the API changes between releases (`1.0.0`, published 2026-10-01)."* The spec simultaneously (a) pins no harness version, (b) promises a schema upstream does not own, and (c) makes that schema the build target for a frontend the §4.3 gate measures for ≥60% reuse. hermes-webui's render path is heavily coupled to message shape (`messages.js` renderers, `assistant_turn_anchors.js:41` "currentSurface: '/api/session messages and message metadata'"), so view-shape drift hits the *expensive* part of the port, not the layout shell.

Fix: (1) pin `@earendil-works/pi-durable` to an exact version in `package.json` and say so; (2) add `GET /v1/meta` returning `{harnessVersion, viewSchemaVersion}` and have the webui refuse to render on mismatch (fail loudly, per this project's own house rule); (3) state that the "documented schema" is *captured from the pinned version* and committed in-repo (a checked-in type/fixture), so upstream drift shows up as a test failure rather than a runtime surprise; (4) make the §4.3 audit explicitly measure render-code coupling, not just layout/theme reuse.

## P1 — must fix before/early in implementation

### P1-1. The memory contract is three seams, not one contract, and the degenerate path poisons the prompt surface

Evidence, §2 memory row: *"three parts: **observe** (a `GenerationHooks.afterResponse`/`onYield` hook …), **recall** (a tool), **inject** (a prompt section)"*; §3.3: *"a `recall` tool that queries harness entries … plus the observe hook writing conversation summaries into a session document."* No interface is named, no observe sink is defined (where do observations go in the degenerate case vs honcho?), and `afterResponse` **/** `onYield` is an unresolved choice — `onYield` fires multiple times per response and changes the payload shape. L1 then replaces three independent seams rather than one object, which is exactly the churn the "thin contract" claim is supposed to prevent.

Second problem: transcript recall is not a graceful degradation. The harness entries it queries are largely *already in context*, so the tool returns what the model can see; the degenerate `inject` is empty while honcho's is a dialectic section. Stranger-sigrun and power-user-sigrun therefore have different prompt shapes and different tool reliability, and the stranger's first impression is "recall is useless" — which is the expectation that then has to be un-taught when honcho lands.

Fix: define one `MemoryBackend { observe(record): void; recall(query): Result[]; section(): string }` in core with the degenerate implementation behind it; pick `afterResponse` only (single fire per turn, replay-safe memo key specified as generation id); and make the degenerate `section()` emit a *stable placeholder* (e.g. "long-term memory backend not configured") so the prompt surface is identical across configurations.

### P1-2. "Image-bearing chat is in scope" has no contract in §5

Evidence, Appendix B.5: *"image-bearing chat is in scope for the webui"*; §5 lists submissions as `{ input, requestId }` with no attachment/content-part shape and no upload endpoint. hermes-webui has a whole upload path (`workspace.js:1354` `/api/workspace/upload`, `ui.js:17838` `/api/file/raw`, `S.pendingFiles` plumbing in `commands.js:1431-1692`). Without a defined write path, M1 cannot implement the submission body and the §4.3 audit cannot judge how much of the composer/tray code ports.

Fix: specify that submissions accept content parts (`{type:"text"|"image", …}`) and name who materializes bytes into the workspace (a `POST /v1/conversations/:id/uploads` returning a workspace-relative path, written via the conversation's ExecutionEnv so §3.4 remote workspaces work).

### P1-3. provider-contributor merge semantics are unspecified at exactly the points M1 must decide

Evidence, §2: *"an extension may contribute `createProvider()` results (pi-ai) + a default model at boot; core merges contributions into one `Models` store before `Harness.open()`"*; §3.1: *"Conversations store extension names, so a deployed extension set change is picked up on restart without touching transcripts."* Unspecified: collision policy for two extensions contributing the same model id; ordering determinism; who wins when two contributors each declare a default; and what a stored conversation pinned to a now-absent model id (`glm-5.3-flash` from `sigrun-ext-bifrost`, bifrost removed) does at submit time. The last one is a live scenario for the "stranger" path and for any extension disable.

Fix: state merge = deterministic last-wins with a logged collision; default model = `SIGRUN_MODEL` overrides any contributor default; unknown model id at submit = explicit 4xx with the available ids (never silent fallback), and record the decision in §2.

### P1-4. The skills convention is a hidden mini-platform, and its discovery scope contradicts §3.4

Evidence, §2 skills row: *"`skills/` in the conversation workspace; SKILL.md frontmatter (agentskills.io shape); rendered as a prompt section + a `load_skill` tool"*. Undefined: frontmatter schema, section content (names+descriptions vs full bodies), section size budget, `load_skill` argument shape and return, collision/priority, hot-reload, and discovery scope. On scope: the workspace is resolved per tool call through the §3.4 wrapper (`env = await workspaceService.forConversation(...)`, ssh/k8s-exec routes when the-work-fabric-scrubbed lands), so "in the conversation workspace" means the skills directory can be remote — a prompt section is normally built once per turn, not per tool call. That interaction is unacknowledged. Scale evidence: hermes grew ~20 skill endpoints plus a full management UI (`panels.js:4917-5310` `/api/skills`, `/api/skills/content`, `/save`, `/delete`, `/toggle`, `/usage`).

Fix: either shrink v1 explicitly — "*skills are read from the local workspace root only; the section carries name + description; `load_skill(name)` returns the file body; no management UI; remote workspaces unsupported in v1*" — or promote skills to a full §-level contract with the frontmatter schema pinned and the per-call env resolution addressed. Do not leave it as a one-line convention that implies both.

### P1-5. Persona is core, but the ship gate requires a persona picker

Evidence, §2 context files: *"`SOUL.md` → persona section, `AGENTS.md` → per-workspace instructions"* (single file, no multi-persona model); §4.1 composer footer: *"persona/profile picker"* as an M2 feature; §3.3/§4.2 confirm hermes' profile machinery is dropped. So M2 must ship a picker over a core convention that has exactly one persona. Either the picker is decorative or the contract is missing.

Fix: make persona a directory convention (`personas/*.md`), store the selection per conversation in `pi.agent` (the same place §4.1 already reads "what's enabled per conversation" from), and define the default when none is selected; or drop the picker from M2 and note persona selection as an L-lane.

### P1-6. The L3=cutover-gate ordering contradicts §1.2's own definition of the cutover gate

Evidence, §1.2: *"**Cutover gate (hermes → 0):** memory + scheduled jobs + agentic-maintenance parity reached."* §7 L3 exit: *"scheduled jobs and agentic-maintenance parity → hermes scales to 0"* — memory (L1) is silently a prerequisite but is not named in L3's exit, while §7's preamble says *"Lanes do not block each other."* An implementer reading L3 in isolation would scale hermes to zero with memory unimplemented.

Fix: L3's exit = "cron + agentic-maintenance landed"; add an explicit "cutover gate = L1 + L3 both exited (and L2 if research is required for daily use — see P1-7)", and restate that lane independence is an *implementation-order* property, not a gate property.

### P1-7. The ship-gate criterion is not testable as written, and it excludes the user's primary use

Evidence, §7 M2 exit: *"user works a full day in sigrun-webui at hermes-with-nothing-enabled parity. Any feature gap that forces a fallback is filed as a Card and fixed before the cutover gate."* Two defects: (a) "hermes-with-nothing-enabled" is undefined — hermes with extensions off still has its full tool/config surface, so "parity" has no checklist and no pass/fail observation; (b) CONTEXT §2 states the dominant use: *"**Research.** The most common use. 'Go find out about X.'"* — which is L2, *after* the ship gate. A full day of sigrun-without-research will force a fallback to hermes by construction, so the criterion as written cannot be satisfied in spirit and will be argued about at M2.

Fix: define the gate as a written checklist of N concrete interactions (drawn from §4.1) executed against a frozen hermes config snapshot, with "a full day" as the soak *after* the checklist passes; and either pull L2 (research) into the ship gate or reword the gate to "harness+webui parity" and move the daily-soak gate after L2. Say which.

### P1-8. Auth/trust boundary is unstated for a write-capable API on the tailnet

Evidence, §4.4: *"Ship gate: Authelia at the ingress … No in-app auth."* §6.1: *"Tailscale LB (`tailscale` class) at `sigrun.tailnet.example.test`"*. §5 exposes writes (submissions, abort, configure) with no auth and no CSRF story; the webui is same-process static assets, so any tailnet host can post to the API directly. For a single-user homelab this is acceptable, but it is currently implicit.

Fix: one paragraph in §4.4 stating the trust boundary (tailnet = trusted principal; the API assumes a single authenticated user), that no endpoint ever accepts or returns credentials, and that the Authelia-fronted ingress is the only public path.

### P1-9. Notification/push and away-from-desk use have no seam

Evidence, CONTEXT §2: *"**Steering coding work from away from the desk.** … answering a pi session's questions or prompt it to continue while on a phone"*; §5 watch frames are per-client SSE connections. Nothing defines completion notification or what a phone client subscribes to without holding a conversation open. hermes-webui has real push plumbing (`sw.js:177-206` notificationclick, `notifications_enabled` in settings).

Fix: state v1 explicitly — "watch frames are the only event channel; push/notifications are a later client concern" — so the webui port does not carry over a settings surface (`sw.js`, notification prefs) with no backend, and so the audit knows what to drop.

## P2 — report-only

- **`configure` is a hole.** §5: *"`POST /v1/conversations/:id/configure` — model/thinking/extension changes via `configure()`"*. Enumerate accepted fields, validation, and whether extension changes mid-conversation are legal given §3.1's "conversations store extension names".
- **abort semantics.** §5 lists *"`abortSubmission` / `Conversation.abort`"* — pick one; state per-submission vs per-conversation and idempotence (hermes' client is fire-and-forget and only reads `cancelled:bool`, `boot.js:35-79`).
- **observe memo key.** §2's "memo-guarded against replay double-observe" needs a key definition (generation id vs entry hash) — folded into P1-1.
- **Env-based secrets with one process.** §6.1: *"Secrets … passed as env; extensions read env"* — every extension (and any env-reading tool) sees every credential. One sentence noting extensions are trusted code with no capability isolation.
- **Estimates.** §7: *"M0–M2 ≈ 4–6 days"* includes port-or-rebuild of a ~170KB frontend against a new API; the rebuild branch alone is 2–4 days optimistic. Add: "if the §4.3 audit lands <60%, M2 is re-baselined before work starts."
- **Discord is both a channel client and a memory peer.** §2 channels vs §3.3 L5 "channels as synthetic honcho peers" — state whether Discord ingestion writes into the shared root conversation or only into honcho.
- **Cron-origin sessions.** §4.1's sidebar has no story for sessions created by cron jobs; hermes has explicit `session_source === 'cron'` handling and unread-dot scoping (`sessions.js:981-1074`). One line in §5's session-meta document for `source`.
