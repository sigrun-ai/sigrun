# Sigrun: a pi-durable personal assistant

**Status:** Draft, pre-implementation
**Date:** 2026-10-02
**Repo:** `~/repos/sigrun`
**Consumes:** `the-work-fabric-scrubbed` (agent-agnostic work fabric) as a dependency, owns none of it.
See `~/repos/the-work-fabric-scrubbed/docs/superpowers/specs/2026-10-02-the-work-fabric-scrubbed-fabric.md`.

---

## 1. What this is

Sigrun replaces `hermes-agent` + `hermes-webui` as user's personal
assistant. Named for the Norse valkyrie Sigrún — a female messenger/attendant
figure, the semantic match for hermes's role without the gendered "female
hermes" construction, and Norse so it doesn't clash with the bifrost gateway.

It is a **pi-durable harness with a webui and a small set of task extensions**,
not a monolith. The hermes features that matter are preserved (persistent
memory via honcho, web-research, scheduled jobs, agentic-maintenance management, the
webui). The ~90% of hermes's config surface that is dead weight post-gateway
(bedrock, docker sandbox variants, personalities, MoA) is gone by construction.

### 1.1 Decoupling boundary

| Layer | Owner |
|---|---|
| Conversation runtime (durable, resumable) | `@earendil-works/pi-durable` (npm, upstream) |
| Workspace routing + cross-agent cards | `the-work-fabric-scrubbed` (this is a consumer, not the owner) |
| Long-term persona memory | `honcho` (already deployed) |
| Model routing + auth | `bifrost` (already deployed) |
| Everything else — webui, cron, agentic-maintenance tools, discord ingestion, forgejo tools, honcho integration | **sigrun extensions** |

If the-work-fabric-scrubbed vanished tomorrow, sigrun still runs with static workspace config.
That's the test of true decoupling.

## 2. The bridge pattern (how sigrun uses the-work-fabric-scrubbed)

Day 1 deployment reality is that hermes (or opencode, or a pi session) already
*can* reach a shared workspace: hermes's ssh terminal backend, pi's
`pi-ssh-remote` extension, etc. The bridge pattern documents this honestly:

> Today each agent is statically configured to point at the workspace. When
> the-work-fabric-scrubbed's pi adapter exists, the *same* workspace becomes `the-work-fabric-scrubbed:workstation-repos`
> resolved through the registry. The behavior is identical; what changes is who
> decides the route.

This matters because it means sigrun's M1/M2 can ship **before** the-work-fabric-scrubbed exists:
point the harness at a hardcoded local path in-cluster, write the
`workspaceService` wrapper that later swaps in the-work-fabric-scrubbed resolution, and nothing
else changes. Fabric integration is a wrapper swap, not a rewrite.

## 3. Architecture

### 3.1 Process layout

One Deployment, single replica (RWO PVC, Recreate). Two containers OR one — decide
at helm time; the API boundary is what matters:

- **sigrun-harness** — the pi-durable harness. Owns the conversation SQLite
  (`/data/sigrun.sqlite`). PI-durable `Harness.open(storage, {...})`,
  `harness.resume()` on start.
- **sigrun-webui** — the thin web client (§4). May be folded into the same
  process as a static-asset + reverse-proxy for the harness API.

The harness exposes a WebSocket/SSE API (see §5) that the webui consumes.

### 3.2 Model access

- pi-ai custom OpenAI-compat provider pointed at bifrost:
  `https://llm-gateway.tailnet.example.test/v1`, VK `vk-sigrun` (to create).
- Default model: `glm-5.3-flash` (mirrors current hermes config).
- **M1 step 0 (30 min):** confirm pi-ai exposes a programmatic
custom-provider/base-URL path. The README only documents built-ins. If the
programmatic path is absent, the fallback is: ship a small local
`@the-work-fabric-scrubbed/pi-ai-bifrost-provider` package that wraps pi-ai's built-in
`openaiProvider({ baseURL, apiKey })` configuration — pi-ai's OpenAI
provider takes both, and pi itself already presets them for bifrost in
`~/.pi/agent/models.json`. Either route lands at the same §5 API; the
difference is two files of wrapper code.

### 3.3 Extensions (the only thing sigrun builds)

| Extension | Purpose | Notes |
|---|---|---|
| `sigrun-ext-honcho` | Persistent memory | User peer config (observe user+assistant, dialectic max, hybrid recall); parity with current hermes honcho block |
| `sigrun-ext-web-research` | Web search + fetch | Tool wrapping searxng + crawl4ai via their HTTP APIs |
| `sigrun-ext-cron` | Scheduled jobs | pi-durable's timer+child-task machinery; port of hermes crontask |
| `sigrun-ext-agentic-maintenance` | media-tools/agentic-maintenance/agentic-maintenance/agentic-maintenance/agentic-maintenance | 1:1 port of the tool logic in hermes's toolsets |
| `sigrun-ext-forgejo` | Forgejo API | create repo, file issue, read PR, commit spec. Used by the "idea → repo+spec+card" flow |
| `sigrun-ext-kanban` | Card operations | thin client over the-work-fabric-scrubbed's skuld API (§4 of the-work-fabric-scrubbed spec) |
| `sigrun-ext-discord` | Read-only Discord ingestion | channels as synthetic honcho peers; v1 read-only |

Memory model: each user = a honcho peer; sigrun = a honcho AI peer. Same
workspace (`user`), same observation policy as hermes's current config.
Discord channels become synthetic honcho peers with ingested log transcripts —
"catch me up on #model-talk" is a dialectic query.

### 3.4 Workspace resolution (the-work-fabric-scrubbed bridge)

The harness's `env()` builder — the thing pi-durable calls per tool call to get
an `ExecutionEnv` — is a thin wrapper:

```typescript
const env = await workspaceService.forConversation(conversation, defaultPrefs);
```

Day 1 implementation: `workspaceService` is a static config (`{ defaultWorkspace:
{ type: "local", path: "/home/sigrun" } }`). When `the-work-fabric-scrubbed-pi` exists, the
implementation swaps to `registry.resolve(name, agentLocation)`; the wrapper
signature doesn't change. M1 ships with the static version.

## 4. The webui

The flagship artifact. **Goal: hermes-webui's UX, shamelessly, rebuilt as a
thin client.** This is the surface the user lives in; everything else is
plumbing.

### 4.1 What to take (feature parity list)

- Three-panel layout: sessions sidebar (pinned/tagged, `⋯` menu), chat center,
  on-demand workspace file browser right panel.
- Composer footer: model picker, persona/profile picker, workspace picker,
  context-usage ring.
- Tool-call cards, expandable, streamed.
- Light/dark + accent theme system.
- Per-session persistent composer draft.
- "Steer" — injecting text into a running session.
- Cron job list (read-only; create/edit in v2).

### 4.2 What to explicitly drop

- The backend entirely (no Python, no second agent loop).
- Provider/credential management UI (bifrost owns that).
- Profile `.env` management (hermes-profile commedia-toolsity — dead).
- The plugin management UI (pi-style package.json at deploy time, not runtime).

### 4.3 Stack decision — port, with a concrete gate

**Decision: port hermes-webui's frontend.** It is Python + vanilla JS (~170KB
of framework-free code) with no build step — Python is the backend and the JS
is the client. Sigrun replaces the Python backend with the harness API (§5)
and keeps the JS unchanged where its API calls allow it.

Gate: M2 begins with a 4-hour audit of `nesquena/hermes-webui`'s file tree
(the JS/HTML/CSS only — the Python is never ported). If <60% of the frontend
is reusable as-is (API calls replaced, layout/session/theme logic intact),
fall back to **rebuild**: TypeScript + React against the harness API, using
the pi-durable vacation demo's structure as reference. The 60% threshold is
measured as: lines of frontend code that survive unchanged into sigrun ÷
total frontend lines in hermes-webui.

The audit is part of M2, not a blocking pre-milestone: its output is the
port/rebuild choice recorded in the M2 report, and both paths end at a UI
shipped against §5.

### 4.4 Auth & access

- v1: Authelia at the ingress (same pattern as grafana). No in-app auth.
- v2: in-app OIDC SP (the multi-user household case).

## 5. Harness API surface (what the webui talks to)

The thin contract the webui depends on. v1 exposes exactly:

```
GET    /v1/conversations
GET    /v1/conversations/:id               -> transcript view (paginated)
POST   /v1/conversations/:id/submissions   { input, requestId } -> submission
GET    /v1/submissions/:id                 -> status (pending/done/unanswered)
GET    /v1/conversations/:id/watch         -> SSE stream of entries
POST   /v1/submissions/:id/abort
```

Transport: SSE for `watch`, REST for everything else. This is deliberately a
subset of what pi-durable offers natively — do not re-export fork/steer/etc
until the webui grows UI for them.

`requestId` makes submissions exactly-once; the webui generates one per draft
send so double-clicks / retries don't double-submit.

## 6. Deployment

### 6.1 Chart

Chart name: **`sigrun`** in `~/repos/helm-charts` (separate from the the-work-fabric-scrubbed
chart — the two services have independent release cadences, and sigrun is the
dependent, so it must not ride on the-work-fabric-scrubbed's helm lifecycle). Modeled on
`hermes-pantheon` but ~⅓ the size:

- Deployment: single replica, `Recreate` (RWO PVC), worker nodeSelector + dedicated toleration
- PVC: `4Gi` `REPLACE-nfs-node`
- Service: ClusterIP; Tailscale LB (`tailscale` class) at
  `sigrun.tailnet.example.test`
- ServiceMonitor + minimal PrometheusRule (process up, sqlite busy)
- Secrets: SealedSecrets for honcho, forgejo, BIFROST_VK, searxng, crawl4ai
- (When the-work-fabric-scrubbed exists:) ConfigMap for the-work-fabric-scrubbed registry endpoint

### 6.2 Dependencies (already deployed)

- honcho (`http://honcho-app-api.honcho.svc.cluster.local`)
- bifrost (`https://llm-gateway.tailnet.example.test`)
- searxng, crawl4ai (existing services)
- forgejo API (token sealed)
- the-work-fabric-scrubbed registry (when T1 lands)

## 7. Milestones

### M0 — pre-flight (½ day)
- Confirm pi-ai custom-provider API (§3.2 verification)
- Create `vk-sigrun` in bifrost
- Root repo layout: `package.json`, `docs/`, `src/harness/`, `src/extensions/`,
  `src/webui/`

### M1 — Harness skeleton (1–2 days)
- npm-install `@earendil-works/pi-durable` + pi-ai
- Programmatic custom provider wiring to bifrost
- One conversation, SQLite on PVC
- `submit`/`wait`/`watch` SSE endpoint
- Static `workspaceService` (local path)
- Deployment on worker nodes
- **Exit:** text assistant reachable via curl; pod restart resumes

### M2 — WebUI (2–4 days) — *flagship*
- Step 0: §4.3 audit (4 hours), records the port/rebuild choice for this
  milestone in the M2 report
- Port or rebuild hermes-webui UX against §5 per that choice
- Three-panel layout, composer footer, tool cards, context ring, themes
- **Exit:** user works a full day in sigrun-webui without opening hermes-webui;
  any feature gap that forces a fallback is filed as a Card and fixed before M3
  ends

### M3 — Memory + research (2 days)
- `sigrun-ext-honcho` (parity with current hermes honcho values)
- `sigrun-ext-web-research`
- **Exit:** "what did we discuss about X last week" works; search works from
  the composer

### M4 — Cards + forgejo (1–2 days)
- `sigrun-ext-kanban` (against the-work-fabric-scrubbed-skuld)
- `sigrun-ext-forgejo`
- "Turn this into a spec + repo + card" demo from the webui
- **Exit:** the-work-fabric-scrubbed's first real external consumer

### M5 — Cron + agentic-maintenance (2 days)
- Port crontasks the user actually uses
- Port the agentic-maintenance tools
- **Exit:** hermes scaled to 0

### M6 — Discord + workstation workspace (2 days)
- `sigrun-ext-discord` synthetic honcho peers, read-only
- Once `the-work-fabric-scrubbed-pi` exists: swap `workspaceService` to resolution
- **Exit:** discord digest works; assistant reads workstation files via the-work-fabric-scrubbed

### M7 — decommission (½ day)
- hermes namespace scaled to 0 or deleted; PVCs retained as archive
- All hermes-specific repo cruft evaluated for deletion

**Total v1 estimate: ~1.5–2 weeks focused work** (not including the the-work-fabric-scrubbed
sibling). The two projects can run in parallel: the-work-fabric-scrubbed T1/T2 independently of
sigrun M1/M2; they join at sigrun M4.

## 8. What sigrun does not do

- Coding-agent work. pi + herdr own that. Sigrun creates cards; pi claims.
- Workflow/claim automation in v1.
- Multi-user UI in v1 (schema carries `owner`, that's all).
- Write-side of Discord.
- Voice/TTS. Deferred to v2 as its own spec; the §5 API is the documented
  intake, so no Sigrun changes are needed to add it later.
- Generalized "honcho-for-things". Skuld's `owner` and `workspace_ref` fields
  are the seam for it, but it's a separate project (likely `skuld` internally).

## 9. Relationship to the-work-fabric-scrubbed (one paragraph)

Twill provides the registry and the resolve/route protocol so sigrun's
extensions can *also* be used by pi, hermes, opencode, cursor without
re-implementation. Sigrun is the the-work-fabric-scrubbed **adapter's first customer at scale**:
its honcho memory, webui, and cron extensions exercise every object kind in
the-work-fabric-scrubbed except AgentProfiles. If sigrun and the-work-fabric-scrubbed were started by different
teams they would still fit; they happen to be the same team.

## Appendix — constraints from the design conversation

The user (user) stated these explicitly; the spec encodes them:

- It must be possible to grow into multi-household use, but day 1 is single-user.
- Away-from-desk steering of pi coding sessions is a must-have… *and* it
  already works via `herdr --remote` today; sigrun only needs to surface the
  link (via Card's `claimed_by`).
- Cron jobs must be crash-durable.
- The webui is the primary surface, not a second-class citizen to a CLI.
- Keep pi's philosophy: minimal core, well-defined interfaces, extension
  ecosystem. hermes's marginal value was concentrated in a half-dozen tools
  and the memory system; everything else is cost.
