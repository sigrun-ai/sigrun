## 1. What this is

Sigrun replaces `hermes-agent` + `hermes-webui` as the user's personal
assistant. Named for the Norse valkyrie Sigrún — a female messenger/attendant
figure, the semantic match for hermes's role without the gendered "female
hermes" construction, and Norse so it doesn't clash with the bifrost gateway.

It is a **pi-durable harness with a webui and a small set of task extensions**,
not a monolith. The hermes features that matter are preserved (persistent
memory via honcho, web-research, scheduled jobs, agentic-maintenance management, the
webui). The ~90% of hermes's config surface that is dead weight post-gateway
(bedrock, docker sandbox variants, personalities, MoA) is gone by construction.

### 1.1 Core vs extensions

Sigrun's **core** is: the harness process, the webui, the surface contracts
(§2), and degenerate defaults for every surface. The core contains no
model-provider code, no memory backend, no cron jobs, no agentic-maintenance tools. Every
capability beyond the degenerate defaults arrives as an extension package.

The design test: **a stranger downloads sigrun, sets three env vars
(`OPENAI_BASE_URL`, `OPENAI_API_KEY`, `SIGRUN_MODEL`), and has a working
durable chat assistant with a webui.** Everything the user personally
wants — bifrost, honcho, agentic-maintenance, forgejo/cards, discord — is an extension on
top, and its absence degrades gracefully rather than breaking.

### 1.2 Two gates

- **Ship gate (v0):** functional webui over the durable harness, at
  *hermes-with-nothing-enabled* parity: chat, model selection, durable
  resumable sessions, context files, degenerate memory and context
  management. No memory backend, no cron, no agentic-maintenance.
- **Cutover gate (hermes → 0):** memory + scheduled jobs + agentic-maintenance parity
  reached. Shippable ≠ cutover; the webui can be the daily surface well before
  hermes scales down.

### 1.3 Decoupling boundary

| Layer | Owner |
|---|---|
| Conversation runtime (durable, resumable) | `@earendil-works/pi-durable` (npm, upstream) |
| Workspace routing + cross-agent cards | `the-work-fabric-scrubbed` (sigrun is a consumer, not the owner) |
| Long-term persona memory | `honcho` (already deployed) — via `sigrun-ext-honcho` |
| Model routing + auth | `bifrost` (already deployed) — via `sigrun-ext-bifrost` |
| Everything else — webui, surface contracts, extensions | **sigrun** |

If the-work-fabric-scrubbed vanished tomorrow, sigrun still runs with static workspace config.
If honcho vanished, sigrun still runs on transcript-recall memory. That's the
test of true decoupling.

## 2. Surface contracts

The core defines one named interface per capability surface. Extensions plug
into these; nothing else is coupled. Where pi-durable already provides the
mechanism, the contract is "use it as-is"; sigrun invents only what upstream
does not have.

| Surface | Contract | Inventor | Degenerate default |
|---|---|---|---|
| **Tools** | pi-durable `defineTool` — TypeBox schema, `replay: "safe"/"unsafe"`, per-call ExecutionEnv | upstream | none needed |
| **Skills** | `skills/` in the conversation workspace; SKILL.md frontmatter (agentskills.io shape); rendered as a prompt section + a `load_skill` tool | **sigrun convention** | directory scan; empty = none |
| **Memory** | one interface: **`MemoryBackend { observe(record), recall(query), section() }`**. Observe rides the `GenerationHooks.afterResponse` hook (pinned choice: single fire per turn; replay-guard via a durable memo keyed by generation id — exact semantics verified in M1, §7). `recall` is a tool; `section()` injects the memory block into the system prompt | **sigrun contract** | `MemoryBackend` over harness entries: recall searches full entry history (including compaction-dropped entries beyond the live context window), `section()` emits a stable placeholder ("long-term memory backend not configured") so the prompt surface is identical across configurations |
| **Context management** | pi-durable's compaction task: policy (`reserveTokens`, `backgroundTokens`) in core settings; `CompactionHooks.beforeCompact` may decline/replace the summary; summarizer model is choosable per policy | upstream + sigrun policy | pi-durable defaults, tuned (§2.1) |
| **Context files** | section loaders keyed by convention: `SOUL.md` → persona section, `AGENTS.md` → per-workspace instructions, read via the conversation's ExecutionEnv | upstream sections | present |
| **Model providers** | **provider-contributor contract**: an extension may contribute `createProvider()` results (pi-ai) + a default model at boot; core merges contributions into one `Models` store before `Harness.open()` | **sigrun contract** | env-driven OpenAI-compat provider |
| **Channels** | clients of the §5 API (submit + watch). Webui, CLI, Discord — all equal clients; no in-process privilege | §5 API | webui |
| **Scheduled jobs** | pi-durable `defineTask` state machines; `runtime.sleep(until)` is a durable wait (survives restart, rechecks the harness clock); `watchDoc` for event-driven wake | upstream | none |
| **Workspace** | `HarnessOptions.env` → the `workspaceService` wrapper (§3.4) | sigrun wrapper | static local path |

Of the nine surfaces, sigrun defines exactly three **extension-contributed
contracts** (skills, memory, provider-contributor), each thin; the workspace
wrapper and context policy are core code, not extension contracts. The rest
is pi-durable surface used directly.

**Approvals (part of Tools):** pi-durable's `beforeTool` hook can block a call
or rewrite its arguments — that hook is the approvals seam, and every
approval decision must be stored via the hook's durable memo so a crash
between "user clicked allow" and "tool ran" never re-prompts or re-runs
(upstream pattern). Sigrun's contract: the core ships an approvals extension
with a conservative default (write/exec tools prompt; read-only tools pass),
policy stored per conversation in a document, and the §5 API exposes
pending approvals + a decision endpoint (§5). Extensions declare per-tool
replay safety (upstream field); approval policy composes with it, it does not
replace it.

Boot order: load configured extensions → collect provider contributions (plus
the env default if none contributed) → `Harness.open(models, registry)` →
`resume()`. A failing extension at boot is quarantined (logged, surfaced as a
degraded surface via `GET /v1/meta`), never aborts `Harness.open()` — chat
survives a bad extension release.

### 2.1 Context-management tuning (v1 defaults)

- Background compaction on (pi-durable default policy shape), tuned values
  chosen in M1 against glm-5.3-flash's window.
- The summarizer model is a policy decision, not the conversation model by
  accident: core pins it to the cheapest long-context model available from the
  provider contributions (configurable).
- A vcc-style context-management extension (richer strategies than
  summarize-and-drop) is a **later lane**, not v1 — the hooks are the seam.

## 3. Architecture

### 3.1 Process layout

One Deployment, single replica (RWO PVC, Recreate), **one container**: the
sigrun process runs the harness, serves the §5 API, and serves the webui as
static assets. A second container would add a split-brain surface for zero
benefit at single replica; the chart can split later if the webui ever needs
its own lifecycle.

- **sigrun-harness** — pi-durable `Harness.open(sqlite, { models, registry })`,
  `resume()` on start. Owns the conversation SQLite (`/data/sigrun.sqlite`).
- **sigrun-webui** — static assets + the §5 API, same process.

Extensions are configured at boot (deploy-time list in a ConfigMap; pi-style
package.json, not runtime plugin management). Conversations store extension
names, so a deployed extension set change is picked up on restart without
touching transcripts. A resumed conversation referencing a removed extension
resumes with that surface's degenerate default; the name is preserved in the
conversation record so re-enabling the extension restores it without a
transcript migration.

### 3.2 Model access — `sigrun-ext-bifrost`

Model access is **extension-driven** (§2 provider-contributor contract). The
core ships only the env-driven degenerate provider. A fallback-provider
extension (e.g. direct-to-ollama) is deliberately **not** in the MVP; if
bifrost is down, sigrun is down — an accepted consequence of the gateway-only
policy (CONTEXT §4). It can be built any time as just another contributor.

`sigrun-ext-bifrost` is the first real contributor and the contract's proof:

- `createProvider({ id: "bifrost", auth: { apiKey: { resolve: async () =>
  ({ auth: { apiKey: VK, baseUrl: GATEWAY } }) } }) }` with the
  `openai-completions` stream functions from pi-ai — auth and baseUrl both
  come from `resolve()` (matches the verified shape; note 2026-10-04 below).
- Model list = the gateway chains relevant to an assistant (chat tier), so the
  webui's model picker lists chain names, not raw provider/model pairs.
- Default model: `glm-5.3-flash` (mirrors current hermes config).

**Merge semantics (core, fixed):** contributions merge deterministically,
last-registered wins on provider-id/model-id collision, collisions are
logged (never silent). `SIGRUN_MODEL` env overrides any contributor's default
model. A conversation pinned to a model id that no contributor serves fails
explicitly at submit (4xx listing available ids) — never a silent fallback.

Verification note (2026-10-04): the programmatic path is confirmed working —
`createProvider` + `stream`/`streamSimple` from
`@earendil-works/pi-ai/api/openai-completions`, models carrying
`baseUrl`/`input`/`cost`. A live probe through bifrost with a VK returned a
committed answer on SQLite storage. The provider *auth* lives in
`ProviderAuth.apiKey.resolve()`, not a top-level `baseUrl` field.

### 3.3 Extensions (what sigrun builds)

| Extension | Surface | Purpose | Notes |
|---|---|---|---|
| `sigrun-ext-bifrost` | providers | Gateway routing, VK, chain catalog | First extension; proves the contributor contract |
| `sigrun-ext-honcho` | memory | Peer config for the user's honcho workspace (observe user+assistant, dialectic, hybrid recall) | **Replaces** the transcript-recall default, does not fill a hole. Parity with current hermes honcho block |
| `sigrun-ext-web-research` | tools | searxng + crawl4ai via their HTTP APIs | |
| `sigrun-ext-cron` | scheduled jobs | Port of the hermes crontasks the user actually uses | Durable by construction (`defineTask` + `sleep`) |
| `sigrun-ext-agentic-maintenance` | tools | media-tools/agentic-maintenance/agentic-maintenance/agentic-maintenance/agentic-maintenance | 1:1 port of hermes toolset logic |
| `sigrun-ext-forgejo` | tools | create repo, file issue, read PR. Used by the "idea → repo+spec+card" flow | |
| `sigrun-ext-kanban` | tools | thin client over the-work-fabric-scrubbed's skuld API | Gated on the-work-fabric-scrubbed T1 |
| `sigrun-ext-discord` | channels | Read-only ingestion; channels as synthetic honcho peers | v1 read-only |

Memory model (with honcho): each user = a honcho peer; sigrun = a honcho AI
peer. Same workspace as the existing hermes deployment, same observation
policy as hermes. Discord
channels become synthetic honcho peers — "catch me up on #model-talk" is a
dialectic query.

Degenerate memory (core, no extensions): the `MemoryBackend` over harness
entries (§2) — a `recall` tool that searches full entry history including
compaction-dropped entries (this is real recall beyond the live context
window, not a re-read of what the model already sees), and an `observe` hook
writing per-turn records into a session document. Honest scope: this is
recall of *what sigrun was told*, not learned user modeling — honcho is what
turns it into memory.

### 3.4 Workspace resolution (the-work-fabric-scrubbed bridge)

The harness's `env()` builder — what pi-durable calls per tool call to produce
an `ExecutionEnv` — is a thin wrapper:

```typescript
const env = await workspaceService.forConversation(conversation, defaultPrefs);
```

Day 1: `workspaceService` is static config (`{ defaultWorkspace: { type:
"local", path: "/home/sigrun" } }`). When `the-work-fabric-scrubbed-pi` exists, the
implementation swaps to `registry.resolve(name, agentLocation)`; the wrapper
signature doesn't change. Ship gate ships with the static version.

## 4. The webui

The flagship artifact. **Goal: hermes-webui's UX, shamelessly, rebuilt as a
thin client.** This is the surface the user lives in; everything else is
plumbing.

### 4.1 What to take (feature parity list)

- Three-panel layout: sessions sidebar (pinned/tagged, `⋯` menu), chat center,
  on-demand workspace file browser right panel.
- Composer footer: model picker (fed by provider contributions, §3.2),
  workspace picker, context-usage ring.
- Tool-call cards, expandable, streamed.
- Approval cards for write/exec tool calls (§2 Approvals) with per-conversation
  policy.
- Image/file uploads: composer attachment path (§5 uploads).
- Light/dark + accent theme system.
- Per-session persistent composer draft.
- "Steer" — injecting text into a running session (submit-while-busy, §5).
- **Surface visibility:** what's enabled per conversation (pi-durable stores
  extension selection in `pi.agent`). v1: static deploy-time view; a picker is
  later.
- Cron job list: NOT in the ship gate — it moves to lane L3 with the cron
  extension itself (§7), where it reads `GET /v1/jobs`. At the ship gate there
  is no cron extension, so the panel would render an empty list; the M2 audit
  therefore treats hermes's cron panel as out of scope.
- Notification/push: v1's only event channel is the §5 watch stream; push
  notifications are a later client concern. The audit treats hermes's
  service-worker/notification settings as out of scope (drop, don't port).

### 4.2 What to explicitly drop

- The backend entirely (no Python, no second agent loop).
- Provider/credential management UI (provider extensions own that; v1 surface
  is the model picker).
- Profile `.env` management (hermes-profile commedia-toolsity — dead).
- Runtime plugin management UI (deploy-time extension list, §3.1).
- Persona/profile picker: v1 is a single persona (`SOUL.md`). Per-conversation
  persona selection (directory convention + picker) is a later lane.
- Notification service-worker and notification settings (§4.1: watch stream
  is the only event channel in v1).
- Cron management panel from the ship gate (moves to L3, §4.1).

### 4.3 Stack decision — port, with a concrete gate

**Decision: port hermes-webui's frontend.** It is Python + vanilla JS (~170KB
of framework-free code) with no build step. Sigrun replaces the Python backend
with the §5 API and keeps the JS where its API calls allow it.

Gate: the ship-gate milestone begins with a **4-hour audit of two codebases'**
frontends (JS/HTML/CSS only — no Python is ever ported):

1. `nesquena/hermes-webui` — the primary UX source.
2. `rcarmo/piclaw` (MIT) — a *working* webui-over-pi-agent with the same
   client/server shape; its steering UI, queued follow-ups, scheduled-task UI,
   and model selection are directly relevant patterns even if no code ports.

Threshold: ≥60% of hermes-webui's frontend reusable as-is (API calls replaced,
layout/session/theme logic intact) → port. Below that → **rebuild**:
TypeScript + React against the §5 API, using the pi-durable vacation demo's
structure and piclaw's UX patterns as references. The choice is recorded in
the milestone report; both paths end at a UI shipped against §5.

The audit must also measure **render-code coupling**, not just layout/theme
reuse: hermes-webui's message renderers are coupled to its own message shape,
and sigrun's wire shape is the serialized pi-durable `ConversationView` —
render code that assumes hermes's shape does not port regardless of the
layout percentage. Record, per subsystem, what survives unchanged vs what
must be re-keyed to the §5 schema.

### 4.4 Auth & trust boundary

- **Trust model:** the tailnet is the trusted principal. Sigrun assumes a
  single authenticated user behind the network boundary; the API never
  accepts or returns credentials; the Authelia-fronted ingress (ship gate,
  same pattern as grafana) is the only public path.
- The Tailscale LB path reaches the Service directly and does NOT traverse
  Authelia — that is the documented trust boundary, not an accident. Write
  access on that path is granted by tailnet membership.
- **Bearer tokens (seam, not day 1):** the §5 server reserves a
  bearer-token auth layer (token(s) from a SealedSecret, one per client —
  webui, CLI, future Discord bot) for when non-browser clients arrive.
  Implemented when the first non-browser client lands; not in the MVP.
- Later: in-app OIDC SP (the multi-user household case).

## 5. Harness API surface (what clients talk to)

**Shape: serialized native views, not a bespoke endpoint list.** pi-durable's
`ConversationView` / `watch()` are designed for UI clients ("everything a UI
needs is committed state"). The sigrun server is a thin layer that
authenticates (§4.4), serializes the native view/watch frames, and adds the
few write endpoints clients need. This keeps the webui in sync with upstream
for free and avoids maintaining a second API surface.

Concretely, v1 exposes:

- **Conversation views + watch frames** over SSE — the native
  `ConversationView` (transcript, streaming answer, running tools, queued
  submissions, pending approvals, agent, usage) serialized per the captured
  schema (below), plus a per-conversation `steer` field reflecting
  submit-while-busy queue semantics.
- `POST /v1/conversations` — create a conversation (upstream
  `createConversation()`); returns its id. `GET /v1/conversations` — list
  conversations with their session-meta (below). The root conversation is the
  default; v1 is multi-**session**, single-user.
- `GET /v1/sessions/:id/meta` / `PATCH /v1/sessions/:id/meta` — the app-side
  session metadata (pinned, tagged, archived/hidden, composer draft,
  `source`: `user|cron`). Backed by a sigrun session-meta document/table in
  the same `/data/sigrun.sqlite` (single-process ownership, §3.1). "Delete
  session" = archived flag (entries are immutable upstream); the sidebar
  reads this resource.
- `POST /v1/conversations/:id/submissions` `{ input, requestId }` →
  `conversation.submit()`. `input` carries content parts — text and
  image/file references (§5 uploads). `requestId` makes duplicate submission
  idempotent (API verified upstream; **crash-replay semantics are a named M1
  verification**, §7 — the claim is "idempotent", not yet "exactly-once across
  crash"). Submitting while the conversation is busy queues the input
  (steering/follow-up queue semantics verified in M1).
- `POST /v1/conversations/:id/uploads` — materialize an uploaded file into
  the conversation's workspace via its ExecutionEnv; returns the
  workspace-relative path used in submission content parts. This keeps the
  upload path correct for remote workspaces (§3.4) rather than writing to
  pod-local paths.
- `GET /v1/models` — the merged provider-contribution catalog (feeds the model
  picker).
- `POST /v1/conversations/:id/abort` — `abortSubmission` (per-submission,
  idempotent; conversation-level abort is not exposed in v1).
- `POST /v1/conversations/:id/configure` — model/thinking changes via
  `configure()`; accepted fields enumerated in the captured schema.
- `GET /v1/conversations/:id/approvals` + `POST .../approvals/:approvalId`
  `{ decision }` — pending tool approvals (§2 Approvals) surfaced in the view
  and decided by the client.
- `GET /v1/meta` — `{ harnessVersion, schemaVersion, extensions: [{name,
  status}] }`. The webui refuses to render on schema-version mismatch (fail
  loudly). Also surfaces quarantined extensions (§2 boot order).

**Captured schema:** the serialized `ConversationView`/watch-frame shape is
captured from the pinned pi-durable version and committed in-repo as a type
fixture. Upstream drift then shows up as a test failure, not a runtime
surprise. `@earendil-works/pi-durable` is pinned to an exact version in
`package.json` (no ranges); the upgrade procedure is: read changelog →
snapshot the sqlite file → upgrade on a scratch copy → verify `resume()` +
view serialization → deploy.

Deliberately not exposed in v1: fork, reset, task graph, per-task control.
They exist upstream; the webui grows UI for them before they ship. (The L3
cron panel reads a read-only `GET /v1/jobs` enumeration added with that lane,
not the full task graph.)

**Multi-user seam:** v1 is multi-session but single-user — one user, many
conversations, all owned by the deploy. The multi-user path (v2) adds a
user→conversation mapping document, per-user auth, and an `owner` dimension
on the session-meta resource. The `owner` field exists in schema from day 1;
the flow does not.

## 6. Deployment

### 6.1 Chart

Chart name: **`sigrun`** in `~/repos/helm-charts`. Modeled on
`hermes-pantheon` but ~⅓ the size:

- Deployment: single replica, one container, `Recreate` (RWO PVC), worker
  nodeSelector + dedicated toleration
- **Storage (§6.2)**: two PVCs — the conversation SQLite on a
  local-path/local-RWO class (SQLite safety), workspace artifacts on the cluster's NFS-backed storage class
  if a separate workspace volume is wanted
- Service: ClusterIP; Tailscale LB (`tailscale` class) at
  `sigrun.tailnet.example.test`
- ServiceMonitor + PrometheusRule: process up, `GET /v1/meta` liveness
  (storage writable + resume complete + extension boot outcomes — not the
  same as process-up), plus two wedged-state gauges: oldest in-flight
  submission age, and oldest waking task age (stuck `runtime.sleep` /
  `watchDoc`). These turn "live but stuck" into an actionable alert; a
  crashed pod is already covered by restart + `resume()`.
- Secrets: SealedSecrets for whatever the *enabled* extensions need (bifrost
  VK, honcho, forgejo, searxng, crawl4ai) — passed as env; extensions read
  env, the chart stays extension-agnostic (a stranger's chart values simply
  have fewer secrets). Note: extensions are trusted code with no capability
  isolation — every enabled extension can read every env secret. Accepted
  for v1 (single-user, single trust domain).
- (When the-work-fabric-scrubbed exists:) ConfigMap for the-work-fabric-scrubbed registry endpoint

### 6.2 Storage safety and backup

The conversation SQLite (`/data/sigrun.sqlite`) is the sole durable store for
transcripts, session meta, approval memos, cron task state, and memory
observation records. Its safety requirements:

- **Not on NFS.** SQLite's WAL/shared-memory semantics assume local disk;
  NFS is a documented corruption hazard. The sqlite lives on a local-path (or
  local-RWO) PV on the worker node; NFS remains available for workspace
  artifacts, which reach tools through the ExecutionEnv, not the sqlite.
- **Journal mode pinned** (WAL + `synchronous=NORMAL` on local disk, or
  pi-durable's storage default — confirmed against the shipped package in
  M1) and recorded here once known.
- **Scheduled backup:** nightly `sqlite3 .backup` to the NFS/RustFS path
  (CronJob in the chart), retention ≥ 30 days. Transcript loss is
  unacceptable; everything else is rebuildable.
- **Restore drill in M1's exit criteria** (§7): a restored-from-backup file
  must resume.

### 6.2 Dependencies (already deployed, consumed by extensions)

- honcho (`http://honcho-app-api.honcho.svc.cluster.local`) — via
  `sigrun-ext-honcho`
- bifrost (`https://llm-gateway.tailnet.example.test`) — via
  `sigrun-ext-bifrost`
- searxng, crawl4ai — via `sigrun-ext-web-research`
- forgejo API — via `sigrun-ext-forgejo`
- the-work-fabric-scrubbed registry (when T1 lands) — via `sigrun-ext-kanban` + workspace swap

## 7. Milestones

Structure: **M0–M2 reach the ship gate; everything after is independent
extension lanes** that can land in any order. Lanes do not block each other
and do not block the ship gate.

### M0 — pre-flight (½ day)
- Create `vk-sigrun` in bifrost
- Root repo layout: `package.json`, `docs/`, `src/harness/`, `src/extensions/`,
  `src/webui/`
- (Provider-API verification is done — recorded 2026-10-04, §3.2.)

### M1 — Core skeleton (1–2 days)
- `Harness.open` over SQLite on the local-path PVC, `resume()` on start
- Provider-contributor contract + env-driven degenerate provider
- `sigrun-ext-bifrost` as first contributor (proves the contract)
- Skills convention skeleton (v1 scope: local workspace root only; section
  carries name + description; `load_skill(name)` returns the body; no
  management UI; remote-workspace skill discovery is post-the-work-fabric-scrubbed)
- Context files (`SOUL.md`, `AGENTS.md`) as sections
- `MemoryBackend` (§2) with the degenerate implementation (recall over full
  entry history + observe hook writing per-turn records)
- Approvals extension: conservative default policy + durable memo decisions
- Context-management defaults (§2.1), summarizer pinned to cheapest available
- Static `workspaceService`
- §5 server per §5's v1 endpoint list, including conversation
  create/list, session-meta, uploads, approvals, `GET /v1/meta`
- Deployment on worker nodes
- **Crash-verification battery (exit criteria, not optional):** `kill -9`
  mid-streaming-generation → restart → answer completes or is marked
  aborted; `kill -9` mid-tool-call → safe/unsafe replay semantics documented
  by observation; `kill -9` during background compaction → transcript
  consistent; duplicate-`requestId` submit after crash → single completion;
  hook replay behavior observed and recorded in Appendix C (this determines
  the memory observe-guard design)
- **Exit:** text assistant reachable via curl; pod restart resumes; restore
  from the nightly backup resumes; provider arrived via extension, not core
  config; the crash battery passes with recorded outcomes

### M2 — WebUI → **SHIP GATE** (2–4 days)
- Step 0: §4.3 audit (4 hours, hermes-webui + piclaw; render-coupling
  measured), records port/rebuild; **if the audit lands <60%, M2 is
  re-baselined before work starts**
- Port or rebuild against §5 per that choice
- Three-panel layout, composer footer, tool cards, context ring, themes,
  model picker, approval cards, uploads
- **Exit (ship gate):** a written checklist of concrete interactions executed
  against sigrun-webui — start/switch/archive a session; send text and an
  image; steer a running session; approve/deny a tool call; pick a model;
  read a tool card; theme switch; resume after a pod restart. Every item
  passes with no fallback to hermes-webui. ("Parity" here means harness+webui
  parity for these interactions, not hermes's full extension surface — the
  daily soak follows L1+L2, which restore the two functions the user actually
  lives in: memory and research. The cutover gate (below) is when hermes
  scales down.) A soak day in the webui follows the checklist pass; any
  feature gap that forces a fallback is filed as a Card and fixed before the
  cutover gate.

### Lane L1 — Memory (`sigrun-ext-honcho`) — *first lane, user requirement*
- `MemoryBackend` implementation: observe hook → honcho observe (memo keyed
  by generation id, design confirmed by the M1 hook-replay finding); recall
  tool → hybrid recall; `section()` → dialectic
- Parity with current hermes honcho values
- **Exit:** "what did we discuss about X last week" works; search works from
  the composer

## 9. Relationship to the-work-fabric-scrubbed (one paragraph)

Twill provides the registry and the resolve/route protocol so sigrun's
extensions can *also* be used by pi, hermes, opencode, cursor without
re-implementation. Sigrun is the the-work-fabric-scrubbed **adapter's first customer at scale**:
its honcho memory, webui, and cron extensions exercise every object kind in
the-work-fabric-scrubbed except AgentProfiles. If sigrun and the-work-fabric-scrubbed were started by different
teams they would still fit; they happen to be the same team.

## Appendix A — constraints from the design conversation

The user stated these explicitly; the spec encodes them:

- It must be possible to grow into multi-household use, but day 1 is single-user.
- Away-from-desk steering of pi coding sessions is a must-have… *and* it
  already works via `herdr --remote` today; sigrun only needs to surface the
  link (via Card's `claimed_by`).
- Cron jobs must be crash-durable.
- The webui is the primary surface, not a second-class citizen to a CLI.
- Keep pi's philosophy: minimal core, well-defined interfaces, extension
  ecosystem. hermes's marginal value was concentrated in a half-dozen tools
  and the memory system; everything else is cost.

## Appendix B — revision-2/3 decisions (2026-10-04 interrogation + adversarial review)

Findings from the pre-implementation interrogation (competitor scan + package
verification against `pi-durable@1.0.2` / `pi-ai`) and the 2026-10-04
adversarial reviews (`docs/superpowers/specs/reviews/`), encoded as decisions:

1. **Two gates** (§1.2): ship = webui + bare-harness parity; cutover = memory +
   cron + agentic-maintenance. Milestones restructured into independent lanes (§7).
2. **Everything extension-driven** (§1.1, §2): providers included —
   `sigrun-ext-bifrost` is an extension, not core config. Core owns three
   thin contracts (skills, memory, provider-contributor) and degenerate
   defaults for all surfaces.
3. **Context management is a first-class surface** (§2, §2.1): pi-durable's
   compaction task + `CompactionHooks` are the mechanism; v1 ships tuned
   defaults with a choosable summarizer; richer strategies are a later lane.
   (User context: pi-vcc's role in pi, mapped to pi-durable's native
   machinery.)
4. **Memory without honcho** (§3.3): the core ships transcript-recall memory;
   honcho is a replacement implementation, not a dependency. A stranger's
   sigrun works.
5. **Image input works** upstream (verified live 2026-10-04: base64 image in a
   submission → model answered). The old "vision waits" constraint is dropped;
   image-bearing chat is in scope for the webui. What's still missing upstream
   is image *reads by file tools* — irrelevant to sigrun's toolset.
6. **Cron is concrete** (§2): `defineTask` + durable `runtime.sleep(until)` +
   `watchDoc` wake — verified in the shipped package. No timer-orchestrator
   sidecar needed.
7. **§5 is serialized native views** (§5), not a bespoke endpoint list; plus
   models list, abort, configure. Session-delete semantics and the multi-user
   seam documented.
8. **One container** (§3.1), resolved from the spec's "decide at helm time".
9. **M2 audit covers piclaw too** (§4.3): MIT, same webui-over-agent shape,
   actively maintained; patterns worth taking even on the rebuild path.
10. **Honcho observation hook placement** (§2 memory contract): observe rides
    `GenerationHooks.afterResponse`/`onYield`, memo-guarded so a crash-replay
    never double-observes. This is what makes extension memory reliable, and
    it's a core contract precisely so every memory backend gets it free.
11. **Competitor landscape** (research record, not a spec change): pi-durable
    is 9 days old; Cloudflare shipped an official PiHarness integration;
    `pi-durable-personal-agent` (scaffold), `piclaw` (mature, pre-durable,
    porting), `pi-chat` (Discord/Telegram bridge) exist. No mature
    general-assistant rival. Sigrun's differentiation: honcho-native memory,
    household toolset, forgejo→cards, the-work-fabric-scrubbed consumption.
