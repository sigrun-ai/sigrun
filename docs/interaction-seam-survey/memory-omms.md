# om-memory-system (omms) — Memory-Architecture Inspection
Source: https://github.com/cmdaltctr/omms

## 1. ARCHITECTURE

Hybrid local vector store + LLM distiller + cross-host shared engine. Not a transcript-index and not a knowledge graph: memory records are **LLM-summarized work units** ("user asked X, technical work Y, outcome Z") embedded and searched semantically, plus a separately learned **user-profile** (preferences by category) and a history importer that backfills past sessions via model calls.

Backing store: **libsql/Turso-style local SQLite with F32_BLOB vector columns and DiskANN indexes** (`memories_vec_idx`, `tags_vec_idx`, `vector_distance_cos`), sharded per scope (user/project) under `~/.omms/data` (default `storagePath`, `src/config.ts:197,20`; shard schema `src/services/turso/shard-manager.ts:301-322`; ANN + hybrid scoring `src/services/turso/vector-search.ts:36-180`). A `metadata.db` holds shard inventory; cross-process write locks coordinate OpenCode+Pi+Claude-Code writers on the same shards (`shard-manager.ts:59-90`). Embeddings run **locally by default** via `@huggingface/transformers` + pinned onnxruntime-node (`src/services/embedding.ts:42-91`), default model `Xenova/nomic-embed-text-v1` (`src/config.ts:198`); remote embedding/external APIs are optional.

Record shape (persisted row, `shard-manager.ts:301-322` + `MemoryRecord` `src/services/turso/types.ts:11-27`): `id, content, vector F32_BLOB(dims), tags_vector, container_tag, tags, type, created_at, updated_at, metadata (JSON string), display_name/user_name/user_email, project_path/project_name/git_repo_url, is_pinned`. `metadata` (`src/types/index.ts:5-27`) carries provenance: `source ("manual"|"auto-capture"|"import"|"api"), type, sessionID, host ("opencode"|"pi"|"claude-code"), hostSessionId, sourceType ("live-capture"|"history-import"), sourceEntryIds, sourceFile, importId, promptId, projectPath, gitRepoUrl`. Scoping is by `container_tag` = project tag; user-profile memories live in user-scope shards keyed by `userEmail`.

## 2. CAPTURE

Triggers (Pi adapter, `src/adapters/pi/extension.ts:288-343`): **`agent_settled`** hook → `capturePiSettledWorkUnit` — one capture per settled turn-batch, not per tool call. The work unit bundles user prompt + text responses + tool calls (`CaptureWorkUnit`, `src/core/capture.ts:18-23`); an **LLM call** (`provider.summarize`, `capture.ts:105-113`) decides whether the work unit is memory-worthy (`summaryResult.type === "skip"` → skipped). Trivial prompts are pre-filtered (`src/core/trivial-prompt.ts`). A separate **profile learning** path batches prompts every `userProfileAnalysisInterval` settled turns and makes its own model calls (`extension.ts:320-340`).

Not a plain hook registration but the full event map is documented at `src/adapters/pi/extension.ts:38-45` (docstring): `session_start` → config+warmup+web-app autostart+retry-drain; `before_agent_start` → retrieval; `agent_settled` → capture; `session_shutdown` → idempotent cleanup.

Dedup/idempotency: capture state machine per session with skip reasons `disabled|busy|not-ready|no-window|already-handled|extractor-skip` (`src/adapters/pi/capture.ts:37-113`) — `already-handled` gates replay. Failed captures go to a **retry queue with drain** (`src/services/capture-retry-queue.ts`, `capture-retry-drain.ts`, failure classification via `CaptureAttemptError` with httpStatus/retryAfterMs, `src/core/capture.ts:41-48`), drained on next `session_start`. Background dedup service merges exact/near duplicates by cosine similarity across shards (`src/services/deduplication-service.ts:1-50`). Every attempt writes a diagnostics record (`buildCaptureAttemptRecord`, `capture.ts:133-150`). `<private>`-tagged text is stripped before storage (`src/services/privacy.ts`). Capture is bound to `hostSessionId` + project `container_tag` (path-derived tags, `getTags`), with `excludeCurrentSession` config to filter own memories out of recall.

## 3. RETRIEVAL

Two modes. (1) **Automatic injection**: `before_agent_start` runs `buildRetrievalSection(prompt, dir, sessionId, budget)` (`src/core/retrieval.ts:15-46`) — semantic search with the incoming prompt, optional current-session exclusion, formatted into a system-prompt section wrapped in `<omms-retrieval>...</omms-retrieval>` (`wrapRetrievalSection`, `retrieval.ts:83-86`); default budget `DEFAULT_RETRIEVAL_MAX_TOKENS = 2000` tokens (`src/core/context-budget.ts:8`) with byte-packing (`packContextSection`). Recent-memories session-start injection also exists (`buildRecentMemoriesSection`, `retrieval.ts:69-118`). Compaction re-injection: `formatMemoriesForCompaction` restores the session's own memories after compaction (`retrieval.ts:141-170`). (2) **Model-invoked**: a `memory` tool with modes `add|search|profile|list|forget|help|migrate|list-shards|export|import` and params query/tags/type/memoryId/limit/scope("project"|"all-projects")/fromPath/dryRun etc. (`src/adapters/pi/extension.ts:349-395`).

Ranking: hybrid — DiskANN cosine on content vector + separate tags vector, candidate union over-fetched (limit×4..×16), then **exact distance recompute + keyword-word overlap scoring** in a second pass (`vector-search.ts:36-180`), capped by byte budget. Injected sections are stripped from later capture input so injected memories are never re-captured as user text (`stripRetrievalSections`, `retrieval.ts:92-99`). Max context growth ≈ 2000 tokens/turn, bounded.

## 4. STATE + LIFECYCLE

Durable: all memories + profile + shard metadata in `~/.omms/data/*.db` (SQLite), global config `~/.config/omms/omms.jsonc`, capture-attempt traces, import backfill state. In-process only: capture state machine, prompt batch for profile analysis, warmup flag (`GLOBAL_PLUGIN_WARmUP_KEY`), backfill AbortController — reset on `session_shutdown` (`extension.ts:343-363`). Session boundary: capture is per settled turn; retrieval excludes current session; compaction triggers memory re-injection. Decay/forgetting: `memory forget` tool mode + `maxAgeDays` filter on recent-memories injection (`retrieval.ts:100-103`); pinning (`is_pinned`); no automatic decay of store. Schema versioning: shard metadata rows record embedding `dims` + `embedding_model` with `INSERT OR REPLACE` (`shard-manager.ts:285-299`); model change → embedding-change service re-embeds (`src/services/embedding-change.ts`); explicit migration services (`src/services/legacy-migration.ts`, `migration-service.ts`, `tag-prefix-migration.ts`) and `docs/omms-migration.md` — versioned, deliberate, multi-generation migration history.

## 5. SEAM SURFACE

Registers with pi: events `session_start`/`before_agent_start`/`agent_settled`/`session_shutdown`; one tool (`memory`, 13 modes); a statusline entry `omms:<warming|connected|recalling|capturing|error>` via `ctx.ui.setStatus` (`extension.ts:52-88`); toasts via `ctx.ui.notify`; one command (history import, `registerPiHistoryImportCommand`). Host-facing surfaces beyond the agent: a **shared web app** (`web/` Vite+React: Project memories browser, Memory/import page, Settings with model/embedding/profile controls; API surface incl. `/api/memories`, `/api/search`, `/api/stats`, `/api/settings/*`, `/api/web/status|stop|restart` in `src/services/web-server.ts:940-1270`) auto-started per host with runtime-handoff ("older web app steps aside", `extension.ts:198-220`), auth-token protected (`src/services/web-auth.ts`); plus a CLI (`om-memory-system` bin) for manual ops.

Durable-doc mapping: a memory record is already provenance-rich (host, session, source file, entry ids, timestamps) and human-readable summary content — it maps well onto a **per-record durable document family** (id, metadata JSON, content, tags, pinned flag, timestamps). What must stay private/extension-side: vectors + embedding-model identity (embedding infrastructure, not decision content), capture diagnostics/retry queues, profile-learning batches.

## 6. EXTERNAL DEPENDENCIES

Local-first: onnxruntime-node + `@huggingface/transformers` embedding model download on first use (needs network once; offline after). Capture/summarize and profile learning make **LLM calls** — via host session model (OpenCode/Pi) or configured external API (Anthropic/OpenAI/Gemini/MiniMax etc., `AIProviderType` `src/types/index.ts:29`); Claude Code requires external API. Optional remote embeddings (Turso remote). Node ≥22.14. Web UI on 127.0.0.1:4747. No vector DB service required (local libsql). Not fully offline for capture (LLM), yes offline for retrieval after model download.

## 7. VERDICT

(a) **~55%**. The durable doc-family covers memory records, profile entries and their rich provenance well (records are already document-shaped with metadata, tags, pinning, timestamps), and a generic panel maps cleanly onto the existing web UI concept (browse/filter/forget) — but OMMS fundamentally needs *private embedding/vector state, cross-host shared shards, and LLM-call capture pipelines with retry queues*, which a decision-document seam does not own; retrieval section injection and budget packing stay extension-private.

(b) **Session-bound provenance on records** — OMMS's `metadata` bundle (host + hostSessionId + sourceEntryIds + sourceFile + sourceTimestamp + importId, `src/types/index.ts:5-27`) is the strongest primitive approvals/interactions/ambient lack: it ties a durable record to *where in which conversation* it came from, enabling current-session exclusion, compaction re-injection, and cross-host deduplication. A close second: the capture-attempt diagnostics/emit record (outcome, failureReason, duration) as an ambient-style health surface.
