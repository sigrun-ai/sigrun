# Ambient Surfaces — pi-zentui (REPO: /tmp/pi-ext-inspect/pi-zentui)

Zentui is a chrome/SKIN extension: it replaces Pi's own ambient chrome rather than adding new persistent surfaces. Its ambient contribution is (1) a fully-owned footer/statusline, (2) ownership of the Working (loader) line incl. settled turn summaries, (3) third-party extension status segments it re-renders, (4) editor/user-message/thinking styling (not ambient status panels). It adds NO zen overlays, NO panel widgets, NO dashboards. Update triggers: event-driven (agent_end, tool_execution_start/end, message updates) + interval timers; render via tui.requestRender().

## 1. SURFACES
- **Starship footer / Hidden footer** (footer.ts:214,1099, `ctx.ui.setFooter`): always-present footer slot. Content: cwd, git branch/status/commit/metrics, runtime, context, tokens, cost, model/provider + optional segments. Placement = footer statusline; 1–2 rows (reflow) with L/M/R zones and a template format; budget rules = terminal innerWidth with per-chunk left/right budgets, truncation with "…" (`footer-layout.ts`, `fitStatusTexts`, `truncateFooterText`); `responsive` + `compactFormat` fallback. Cadence: event + interval (git poll, time, session duration). Per-extension status segments placed "off|left|middle|right" (config.ts:373), "Hidden" style = single row with fair L/M/R budgets (extension-status.ts `layoutExtensionStatusLine`). Persistence: **none** (in-memory, rebuilt each session); config persisted in `~/.pi/agent/zentui.json` (config.ts:539). Survives /reload via config re-load, not state.
- **Working line** (working-line.ts): optional ownership of the in-progress loader row above the editor (`placement: "above" | "border"`). Spinner frames (≤1024 frames, ≤80 row cells), animated message text (≤48 messages, ≤43 cells), live segments (tool/elapsed/thought/tokens/tokenRate), metric updates throttled to 50ms. Persistence: none. Cleared when idle.
- **Turn summary** (interaction-summary.ts): settles each agent turn into a `pi.appendEntry("zentui-turn-summary", summary)` transcript entry (index.ts:2044) rendered later via `registerEntryRenderer` (index.ts:263) — the ONLY persistent surface (session JSONL). Versioned shape incl. duration, in/out tokens, think time, avg rate, style prefix, format.
- **Extension status controller** (extension-status-controller.ts): monkey-patches `ctx.ui.setStatus` (pi's keyed status-slot API) to hide/replay third-party statuses per visibility policy; shows that pi already HAS a keyed status-slot primitive (A's model).
- **Selector borders / editor frame live metadata** — cosmetic, non-status.

## 2. DATA MODEL
- Footer transient state: `FooterState = GitStatusSummary & { modelLabel, modelId, modelName, providerLabel, contextLabel, tokenLabel, cacheReadLabel, cacheWriteLabel, costLabel, usageTotals {input,output,cacheRead,cacheWrite,latestCacheHitRate,cost}, subscription, autoCompaction, runtime?, packageVersion?, sessionStartEpoch? }` (state.ts). Config UI is template-driven: `FooterComponentConfig` with `style`, `segments: FooterSegmentsConfig` (booleans), `format`, `responsive`, `compactFormat`.
- Third-party segment (separator of A/B): `{ key, text }` working-line (working-line-extension-segments.ts; caps: 16 segments, 64-key, 256-text code units) and `ExtensionStatusSegment = { key, text, placement, colorMode }` (extension-status.ts) — keyed, string-only, full-replacement publish.
- Turn summary: `TurnSummaryDataV4 { durationMs, input, output, thoughtDurationMs, stylePrefix, format, averageTokenRate? }` (interaction-summary.ts:16-55).
- Pre-rendered string style throughout: segments are composed into colored text lines; statuslines are ANSI strings with sanitization (SGR + OSC8 link preservation).

## 3. INTERACTIVITY
Footers/working line: **read-only** — no keys, no collapse, no navigation, no editing. Human interaction happens only through the `/zentui` settings UI (SettingsList with key handling in settings-keys.ts/settings-list-selection.ts), which edits the zentui.json CONFIG (component toggles, colors, format strings), not the surfaces' live state. Status segments are interactive only insofar as they can carry OSC8 HTTP(S) links (sanitizer preserves them).

## 4. MAPPING
- Footer/statusline segments (cwd, tokens, cost, context…) → **A line**: FULLY (it literally consumes pi's keyed `setStatus` API and owns the footer slot; keyed segments {key,text} = A exactly). The turn-count/limit metrics map to `metrics {tokens?,cost?}` PARTIALLY — present but irrelevant to rendering since payload is pre-formatted strings.
- Working-line live segments (tool name, elapsed, tokens, spinner) → **C gauge**: FULLY (label, phase, elapsed, spinner, token metrics are exactly C's fields); the animated spinner text could fall to `details` for the frame presets themselves (cosmetic).
- Turn summary → **A line** FULLY (one settled line per turn) — D ledger PARTIALLY if consumers wanted history, but v4 has no append/amend model (one entry per turn in Pi's transcript, no enumerable row state).
- Extension-status hide/show segments → **A line** FULLY (keyed slot, exactly the 'one keyed slot per key' promise).
- Nothing maps to **B rows** — zentui has no multi-row enumerable panel. Selection among many items happens in the dialog-style /zentui UI, out of ambient scope.
- Opaque `details` fallback would absorb: spinner frame set + text-animation message list (working-line's richest payloads), format-template strings.

## 5. VERDICT
~85–90% of ambient content covered by {A, C} (A: footer/status segments/turn-summary line; C: working line); D marginal (~5% only if turn summaries need history semantics), B unused (0%). **Most valuable missing primitive: none needed as a shape — the gap is an ENVELOPE rule**, not a data shape: zentui proves ambient payloads are composed of PRE-RENDERED styled strings (theme-colored ANSI, OSC8 links) plus budget policies (responsive/compact, per-zone truncation, throttle cadence like the 50ms metric interval). The channel-neutral spec needs: (a) payload may be exact text segments keyed + placement hints (left|middle|right), (b) first-class string budget/truncation policy on the envelope, (c) a settle-to-persistent-history bridge (turn summary = agent-turn lifecycle → durable entry) which {D ledger} comes closest to but with versioned single-record lifetime rather than append-feed. The human acts ON the surface only via config UI, never edits the ambient state itself — footers are read-only here.
